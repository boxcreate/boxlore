# `:core:catalog`

## Purpose

Owns catalog orchestration: Podcast Index access through `PodcastRepository`, subscriptions, chapters, transcripts, content catalog (v3), cross-promotion, consent helpers, install-referrer handling, backup and restore, and shared dependency bridges used by workers and services. It does not own playback, download workers, Compose UI, Room schemas, RSS internals, or ranking model storage.

## Public API

- Both episode-mapping paths ignore blank episode art before falling back to `feedImage`, retain show art separately and normalize surrounding whitespace/HTTP. Feed mappers also ignore blank `artwork` before `image`. `ArtworkMappingTest` covers blank values and signed artwork parameters without live API calls.

Failed consent writes keep activation off, and local notification flags prevent a failed revoke from implicitly re-enabling after restart. RSS sync isolates each feed and runs alongside PI sync; the source adapter explicitly implements every catalog operation.

- `SubscribedEpisodeCatalog` routes the shared local catalog contract by podcast ID to the PI or true RSS adapter. Shared negative IDs from a source switch resolve to the active subscription rather than a retired PI compatibility row. Foreground refresh, Home tips, Smart Downloads freshness, auto-download discovery and push hydration support RSS-only shows without PI lookups or required promotion. With a `FeedMoveFollower` (the app passes one behind `feed-fix-moved-feed-off`), every refresh of a Podcast Index show through it (the show page, pushes, auto-download, restores, the ingest after a follow) checks for a feed that moved for good (permanent redirects or `itunes:new-feed-url`, same title; the stored title when the caller sent none) and saves the move through the address writer below. Requests that ask for move detection themselves (the background pass) are left to their caller.
- **Saved feed addresses (one writer).** `FeedAddressUpdater` (`SubscriptionRepository.feedAddresses`, `updateFeedAddress(FeedAddressChange)`, `ensureHttpsFeedUrl`, `adoptMovedFeed`) is the only writer of a show's saved address. In one Room transaction (`PodcastDao.replaceFeedAddress`) it writes the HTTPS publisher address and the transport address, keeps the old address in `previousFeedUrl` for undo, records where the address came from (`feedUrlSource`: a `FeedUrlSources` value or the registry's `feedSource`) and when the registry confirmed it (`feedUrlCheckedAt`), clears every stored ETag and Last-Modified of the show (the row, its catalog feed and its feed-only extras), and marks a followed show for the next sync push (not for an address that came from the cloud, and never an unfollowed row, whose push could end the follow on another device). A write the registry didn't confirm keeps the stored daily-check stamp. It is a compare-and-set on the address it read, and `FeedAddressChange.onlyReplacing` narrows it to the address a caller read: a move is adopted only from the saved address that was read (a push or a restore may read another one, `FeedMoveFollower`), and a recovered address replaces only the address that failed. It records the show as pending (`PendingNotificationRegistrations`, the app's `SharedPreferencesPendingNotificationRegistrations`) before the write, and writes nothing (`NOT_SAVED`) when that record couldn't be saved, which no caller treats as done: a cloud pull fails before its pull time is saved (`FeedAddressNotSavedException`), the daily check leaves the show due for the next pass, and a restore reports the show, asks the app to register the show's notifications again when they are on (`FeedAddressWiring.requestNotificationRegistration`; any failure of that request is caught), and clears the mark only once Firebase acknowledged (`registrationSettled`), and only the request the job read before registering (`pendingMark`; each request gets a new mark), so an address change made while a job ran stays pending for the job that replaced it; each foreground pass asks again for every pending show (`resumePendingRegistrations`), so one lost with the process or given up on by the background job is never dropped. It reports a correction of a followed show's address as `feed_url_corrected` (`FeedAddressWiring.telemetry`). `rss:` shows and addresses that aren't HTTPS are refused. A cloud pull never puts back the address a confirmed correction (`FeedUrlSources.isConfirmedCorrection`: the registry, a feed move, a broken-feed report or the `/podcast` re-check) replaced: it returns `KEPT_CORRECTION` and marks the follow for a push, so the account gets the corrected address back. Merges of pulled rows write through `PodcastDao.upsertKeepingFeedAddress`, so an older copy never writes its address over one saved meanwhile. A follow keeps a saved HTTPS address (`FeedUrlSources.followedFeedUrl`), and a missing address from a show's details is filled through the writer. Every writer goes through it: missing-address recovery, the dead-address re-check, moved feeds, broken-feed reports, the daily check, auto-download, backup restores and cloud pulls (`SubscriptionSyncResolver(feedAddresses = …)` saves a pulled address for a Podcast Index show this way and leaves the row clean; without it, as in older tests, the row is written as before).
- **Renumbered shows (one follow).** `RenumberedShowFollows` (`SubscriptionRepository.renumberedFollows`: `adoptAnswer`, `adoptKnown`, `currentId`, `endedFormerFollows`, `collapseFollowsQuietly`) keeps one follow when Podcast Index renumbers a show ([docs/EPISODE_IDS.md](../../docs/EPISODE_IDS.md#renumbered-shows)). `PodcastRepository(onShowRenumbered = …)` reports every details answer for a canonical numeric show ID that names another one, before the answer is returned, so every existing details call detects it (the show page, a cloud pull's enrichment, address recovery). The answer is recorded (`RenumberingWiring.shows`, `boxlore_renumbered_shows` in the app) and a follow of the old show moves to the new one in one transaction (`PodcastDao.moveRenumberedFollow`, rules in `RenumberedFollowMerge`): the new show keeps its own row and namespace, or is created without one, with notifications and auto-download on when either was, and its own genre, icon, sort and trims, else the old show's; it keeps its own follow time or takes the time of the move, never the old show's earlier one, which any later unfollow of the new show on another device would beat in sync. Both rows are read, merged and written inside the DAO's transaction, so a pull or toggle never lands between the read and the write. The old show is unfollowed like any unfollow. Both rows are dirty, so the next push carries the follow and the unfollow, and a pull of the old show's older follow loses to the newer unfollow. Notifications for the new show are recorded pending (`FeedAddressUpdater.markRegistrationPending`) before the row turns them on and then registered through the acknowledged job; the old show's are turned off. Folder memberships, Home pins and the manual order move; the old show's catalog starts its unfollowed countdown; the old show's listener rows are linked to the new show's episodes (`RenumberingWiring.linkEpisodes`, `:core:rss`). A new show followed through its own RSS feed keeps that follow and only the old one ends, its folder, pin and order places moving to the RSS show and only the old show's catalog countdown starting; when the old follow has notifications and the RSS show's doesn't (turning them on needs the listener's consent), both follows stay. `rss:` shows are never touched. Each foreground pass first moves follows of shows recorded as renumbered, then asks details only of followed shows that share a feed address or podcast GUID with another follow, at most six per pass (`RenumberedShowFollows.collapseFollows`, run quietly by the pass, order from `RenumberedFollowMerge.lookupOrder`): a show is asked once per process after an answer, and a failed lookup is asked again on a later pass after the shows not yet asked; a show is never matched by title. `toggleSubscription(podcast, shownFollowed)` decides the direction from what the caller showed (the show page passes its own state, which counts a follow under the old number; other callers show the show's own row): asked to follow, a follow under the old number moves here with its settings; asked to unfollow, every follow of the show ends (`endedFormerFollows`), and unfollowing a followed `rss:` feed also ends a follow kept under a number its show replaced (`endFormerFollowsOf`). A follow moves only once the renumbering is saved; when saving fails it stays under the old number. A toggle never adds a second follow and a Subscribe tap never unfollows. `isFollowedUnderFormerId` tells the show page about a follow still under the old number. The daily address check also passes on merges the server confirmed with Podcast Index (`V2ShowAddress.mergedInto`): `FeedAddressDailyCheck` hands each to `adoptKnown(oldId, confirmedNewId)`, which records the renumbering and moves the follow without a details lookup, and the merged show's own address is never swapped.
- `PodcastNotificationRegistrar` (`SubscriptionRepository.registerPodcastNotifications`) registers a Podcast Index show's notifications again and waits for Firebase to acknowledge both the `tracked_podcasts/<id>` node and the `new_ep_<id>` topic, the same node and topic as turning notifications on. The node is one per show for every follower and its write replaces it whole, so it is written only with an address (once the show has a latest episode); otherwise only the topic is subscribed. `NotificationRegistrationOutcome.RETRY` is retried by the app's capped background job; rules that refuse the write give `DROPPED`.
- **Daily address check.** `FeedAddressDailyCheck` runs at the start of each foreground pass (behind `RolloutSwitches.addressCheck`). It asks `POST /v2/shows/feeds` for every followed Podcast Index show with a saved address not checked in the last day, in chunks of at most 500, and swaps an address only for a confirmed move: the registry flags the show for address repair, the address is the registry's own (`registry:` source), HTTPS (an http-only address is never adopted, since background reads need HTTPS), different from the saved one, and not the address the saved one replaced (whatever replaced it: a feed move, dead-address recovery or a cloud pull). `fetchUrl: null` keeps the saved address. The new address is read first (`DirectFeedRecovery.addressRead`, a catalog refresh from it) and saved only when that read works, so an address the phone can't read never replaces one it can. Each show the registry answered for is stamped (`podcasts.feedUrlCheckedAt`): a swap writes the stamp with the address, and any other show is stamped after its swap had its chance. A failed call or `registryAvailable: false` stamps and swaps nothing. Follows with a change made on this phone that the account hasn't received yet (dirty and synced before) wait for the push; follows never synced to an account are checked. A different `epNs` is only logged (D12).
- **Broken-feed reports.** `FeedReporter` sends `POST /v2/feed-report` (`{id, status}`, never an address) for every failed background read of a Podcast Index show (`RefreshOutcome.Failure.reportStatus`), behind the same switch, never while offline, at most once per show a day and 20 a day in all, the API's own limit (`FeedReportLimiter`, one per app, shared with the show page, which stops 5 short so followed shows always have room; times kept in `FeedReportStamps`, the app's `SharedPreferencesFeedReportStamps`). Only a report the API answered counts: a failed send or a 429 uses up nothing. Its answer is an address to try only when it differs, is HTTPS and the saved address looks dead.
- **Feed address repair after the update.** `UpgradeAddressRepair` (`SharedAppDependencies.upgradeAddressRepair`, run by the app's `UpgradeRepairWorker`) repairs the saved address of every Podcast Index show followed when the phone upgraded; the v39 upgrade seeds one pending `upgrade_repair_shows` row each, a fresh install none. Per show: (1) `POST /v2/shows/feeds` in chunks of at most 500 (`UpgradeAddressCheckStep`, production request `AddressCheckAnswer.fetchWith`); the answer stamps the daily check and records `checkedFetchUrl` only for a confirmed move (`FeedAddressDailyCheck.confirmedMove`), plus the transport address, source and the server's `epNs`. A chunk the server couldn't answer (503, 429, another 5xx, no connection, or `registryAvailable: false`) stays at step 0 without counting a try while the other chunks go on; one it refused (another 4xx) or whose answer couldn't be read counts a try for each show. A show refused 5 times, or unanswered for 7 days since its first failed check (`MAX_UNANSWERED_MS`), goes on without an answer: no swap, and the daily check looks after its address. (2) The swap through the one address writer (`feed_url_corrected`, step `upgrade_repair`; skipped for follows changed on the phone and not pushed yet, which the daily check handles once pushed). An answer more than a day old is asked again at the start of a run (a repair paused or stopped for a while never applies an old answer), and one the daily check has since replaced with a newer answer is not applied. (3) A catalog re-read of the saved address (`rereadWith`; the server's namespace is passed only for comparison, so issued IDs never change, and moves found are followed by the catalog). It never starts the foreground auto-download pass (`runPostPersistCallback = false`): the regular background pass applies the listener's background download rules. (4) Notification re-registration for every followed show with notifications on whose own steps are over, recorded in `UpgradeNotificationMarker` (`FileUpgradeNotificationMarker`, `noBackupFilesDir`) only once the app reports the request saved, so a restored phone registers again even when Room says steps 1–3 are done. Once no show has steps 1–3 left, `UpgradeRepairPorts.onAddressStepsFinished` runs once per install (recorded in the same file; never on a fresh install, while shows wait, or while paused), which the app wires to `UserSyncCoordinator.requestIdentityCatchUp`, so history and queue rows whose episodes the reads settled reach the cloud with their identity. Each step is written as it finishes, so process death resumes at the next one; the row is read again before each step, and a show no longer followed ends `done`. A failed re-read while online counts against a cap of 5 tries (`gave_up`); failures while offline never count and stop the run. Shows followed after the upgrade get no row. `needsWork()` settles a fresh install, or one with only `rss:` follows, without network. Behind `RolloutSwitches.upgradeRepair`: off returns `PAUSED` without marking anything done. One `feed_fetch_result` background summary (`source=feed`) per run that read feeds, with `namespaceMismatchCount` for reads of shows whose server namespace differs from the phone's (decision D12).
- RSS notification activation requires explicit public-feed disclosure acceptance through `setNotificationsEnabled(..., acceptRssDisclosure = true, disclosedFeedUrl = savedUrl)`. `DeviceRssNotificationConsent` stores only URL fingerprints in `noBackupFilesDir`; changed URLs, restore and remote cloud settings cannot supply acceptance. Canonical `rss:` IDs require disclosure even with stale source metadata. Refused or revoked activation also removes this device's old registration; a library cleared during acceptance cannot publish a deleted show. Notification settings remain independent of auto-download. The shared checker receives only explicitly accepted public feeds. `TrackedPodcastRtdbLogic.topic` maps `rss:` to FCM-safe `rss_` while retaining canonical IDs in payloads. JSON/cloud RSS restore retains the original saved show ID across redirects.
- RSS topics and per-device registration keys include a SHA-256 hash of the exact trimmed accepted URL. `DeviceRssNotificationRegistrations` keeps an atomic publication/cleanup journal in `noBackupFilesDir`, containing fingerprints and keys rather than URLs. Activation fails closed if the journal cannot be saved. `RssNotificationReconciler` awaits both RTDB and FCM acknowledgement, retains active entries and failed cleanup obligations, and retires old URL scopes or deleted/disabled shows. Live RTDB rules refuse whole-node deletes, so cleanup keeps the node and removes only its `feedUrl` child, which the checker needs to poll an RSS scope. The rules refuse that delete only when no node exists for the key (for example a legacy key this device never published), so a refusal still unsubscribes the FCM topic and clears the journal entry; any other failure keeps both. Migration scans disabled and unsubscribed canonical RSS rows too, removes legacy device keys/topics, and rejects restored notification flags without local consent. `canPresentEpisodeNotification` verifies the current saved URL, subscription, enabled flag and device-local acceptance.

- `PodcastRepository` coordinates Podcast Index calls, recommendation endpoints, curated vibes, home bootstrap, similar episodes (with content languages), content catalog/v3, user feedback submission (`submitFeedback` transmitting categorized feedback, repro steps, optional email, and diagnostics to proxy), and RSS delegation. Canonical `PodcastEntity.toPodcast()` mapper standardizes entity conversion across data and feature modules, with module-boundary isolation between `:core:catalog` and `:core:rss`. Subscribed PI shows whose local catalog is **ready** (`LocalEpisodeCatalogPort.isReady`) serve list/search/`getEpisode` from Room only. Unsubscribe stamps a 14-day TTL; that catalog stays on disk but is **not** ready, so unsubscribed reads keep today’s PI pages plus cached extras merge. True `rss:` rows are unchanged. `getEpisodes` uses a bounded window (200), not `getAllNewest`. Followed shows' catalog refreshes never read a Podcast Index list: new episodes take recipe IDs in `:core:rss`. `loadPiEpisodesForSupplement` is the Podcast Index list feed-only extras (`EpisodeSupplementPort`) are compared with: up to 1,000 newest episodes from `episodes/match` (match fields only), falling back to the oldest page (at most 100) when that route fails, returns nothing, or its `useEpisodeMatchBaseline` off switch is set. It is strict, so a failure of both stops the extras refresh instead of comparing the feed with an empty list. Its callers are the show page's "Missing episodes?" refresh, the legacy subscription sync and push paths without a local catalog, and the restore of extras opt-ins; they stay until show pages read feeds for every listener. Full pages keep the 100 cap. `getEpisode` resolves an ID in `EpisodeLinkResolver`'s order without reading a feed: a stored row (local catalog, then the feed-only rows for a negative ID), then the phone's row of the episode the ID is a trusted alias of, then the network. It sends a revcipe-ry canonical positivge ID (`[2^52, 2^53 − 1]`) that no local row or alias holds to `/v2/episode` (with the show when a caller passes `getEpisode(episodeId, showId)` and the show is below 2^52): a recipe-range ID (`[2^52, 2^53 − 1]`)d never reachesto the v1 Podcast Index lookup, and an old Podcast Index ID falls back; to v1 `/episode` only when the v2 route can't answer; other legacy IDs keep v1. The episode keeps the ID asked for and carries the recipe ID and catalog key. A `needsFeed` answer, a 400/404/410 or an error is not found. Podcast Index IDs keep v1 `/episode`. `invalidateEpisodesCache` drops the 5-minute PI page cache for a feed (Podcast Info pull-to-refresh). `PodcastRepository` also owns the `/v2` client (`apiV2`, a `BoxLoreApiV2` built on first use): same base URL and the same cached OkHttp client as `api`, so the process keeps one HTTP cache. Tests can pass `boxLoreApiV2` the same way they pass `boxLoreApi`. `getEpisode` and the discovery routes below use its only caller so far. In-memory caching and pagination safety are managed by `PodcastRepositoryMemoryPolicy` (`clampPageLimit` caps requests to 100, and `TimedLruCache` bounds cache entries with LRU and TTL eviction to prevent OutOfMemoryError).
- **Show page episode source (P4 PR 16).** `PodcastRepository.showPageSource(feedId)` is `RSS` (`rss:` shows), `FOLLOWED_CATALOG` (a ready followed catalog), `FEED` (`RolloutSwitches.feedFirst` on, a Podcast Index show ID, and its feed not found unreadable on this page) or `SERVER_LIST`. Only the show page reads the stored copy: `getShowPageEpisodes` pages a `FEED` show from it (`FeedFirstWiring.copies`, a `ShowPageFeedPort`), more pages following while the copy has rows or isn't the whole archive, and an oldest-first page of a partial copy comes from the server's list. `getEpisodesPaginated` (Smart Queue, Android Auto, Home, downloads, the episode page) never reads the copy, which only the show page reads again. For a show whose catalog isn't ready it reads `/v2/episodes`, its recipe IDs mapped to the phone's owners (`DiscoveryEpisodeIds.toLocalOwners`, so a rollback of the flag shows the same IDs), and v1 `/episodes` only when `/v2/episodes` fails (decision D1). `getEpisodeWindow` and `getEpisodes` use the same IDs: around an episode the feed-first copy holds, the copy's window; else the newest 200 of `/v2/episodes` under local owners; v1 only when that fails (`LEGACY(own-ids)`). `FeedFirstShowPages` (`openFeedShowPage`, `readShowPageFeed`) reads the feed into the copy, `NEWEST` or `ARCHIVE` deep, down the failure ladder: offline shows the copy with no read and no report (`OFFLINE`); the address is the registry's (`/v2/podcast`), else the saved one, and an http-only feed goes through `/v2/feed/<id>` (`v2Transport`: the copy's ETag as `If-None-Match`, the body capped like a direct read with `RssFeedClient.readFeedBody`, a `404 not_proxied` with an HTTPS `fetchUrl` read directly, under the download gate and per-show lock); a failed read is tried once more (not after a 404 or 410), then reported through `FeedReporter.reportTarget` (the app's one `FeedReportLimiter`, leaving `FOLLOWED_SHOWS_RESERVE` of the daily cap to followed shows; never for a followed show, whose own refresh reports and saves addresses), and a different address in the answer is read, through the transport when it is http-only; then the page uses the server's list with a notice (`FALLBACK`) until it is opened again. One `feed_fetch_result` per read (source `feed` or `transport`, `partial` or `complete`). Once a day per process, in the background so a page's first paint never waits, it removes unfollowed copies not opened for 30 days, under a size cap (decision D10). In-show search always runs on the phone: the stored copy (`LIMIT 200` in the query), else the newest 1,000 of `/v2/episodes` matched by title or description; v1 `episodes/search` is never called (decision D16). `invalidateEpisodesCache` also drops pages cached under the Podcast Index ID a `url:`, `guid:` or `itunes:` ID resolved to.
- Episode links, pushes and Android Auto items that name an episode by ID and maybe its show resolve through `resolveEpisodeLink(episodeId, showId, onReadingFeed)` (`EpisodeLinkResolver`, `PodcastRepositoryEpisodeLinks.kt`). Order: a stored row; a trusted alias of the ID, or for a recipe ID with its show the one episode of that show whose trusted aliases carry it, answered with the phone's own row and ID; the API (an answer for an episode stored under another trusted ID or the same key is translated to the phone's row; a v1 answer, which has neither, by its enclosure address); and, for a `needsFeed` answer, one read of the show's feed through the existing reader (`RssEpisodeFeedReader`: the publisher's HTTPS address with `RssFeedClient`, an http-only address only through `/v2/feed/<id>`), matched by recipe ID in the show's stored namespace. Only items whose key follows the contract match; a feed listing the same item twice gives its first copy in document order, and a recipe ID two different keys share matches nothing. Results are `EpisodeLinkResult.Found`, `NotFound` (nothing lists it: 400, 404 or 410) or `Unavailable` (a source couldn't be reached, including 401, 403, 408 and 429). `storedEpisodeForKey(show, key)` finds a stored row by catalog key (the local catalog by GUID or enclosure, then the show's feed-only rows by enclosure); alias, push and link lookups use it. Ambiguous and unresolved aliases never resolve. `EpisodeAliasReads` / `RoomEpisodeAliasReads` are the alias reads (`trustedKeyOf`, `trustedKeyForRecipe`, `namespaceOf`); `PodcastRepository(episodeAliases = …)` takes them (none by default, as in older tests) and `feedReader` is the test seam for the feed read. `localEpisodeForRecipe(show, recipeId)` is the push match by (show, recipe ID).
- Episode share links: `EpisodeSharePreparer` (an `EpisodeShareTargetSource`) names the episode by its trusted alias's recipe ID and Podcast Index show (also for an RSS show linked to that show), else by `EpisodeShareIds.choose` on the episode's fields; phone-only negative or reserved IDs are never shared: an episode held only under one is shared by the recipe ID of its catalog key in the show's namespace, else as the show's link, and `rss:` shows keep today's link. With a known catalog key it registers the episode first through `EpisodeShareRegistrar.registerOnce` (`POST /v2/episodes/register`, `{show, guid, enclosureUrl}` with the audio address so the API can match a GUID that differs from Podcast Index's, or `{show, enclosureUrl}` when the key is the audio address), waiting at most `DEFAULT_TIMEOUT_MS` (2 s); the link goes out whatever the answer, and a timeout, offline, 401, 429 or server error hands the request to `scheduleRetry` (the app's background worker). 400/404 are dropped.
- `syncSubscriptions` (`POST /sync`) is PI-only. `SubscriptionForegroundSync` sends it the shows that are **not** catalog-ready and have no saved HTTPS feed address, plus the shows whose own feed failed this pass. The PI ids go out in chunks of 20 (`PI_SYNC_CHUNK_SIZE`), at most two calls at a time (`PI_SYNC_PARALLELISM`), because the API serves only the first 40 ids of a call: whole-library callers (Smart Downloads, backup restore) used to lose every show past the 40th. A failed chunk drops only its own shows' tips. Ready ids contribute the Room newest tip; opted-in not-ready ids contribute the cached extras tip. Live feed freshen stays on `SubscriptionForegroundSync`. `getEpisodeWindow` is the bounded Smart Queue / Auto entry (never `getAllNewest`).
- Show search: legacy `searchPodcasts` / `searchPodcastsWithCorrection` keep calling `GET /search` (hybrid). New clients use `searchPodcastsTypeahead` (`GET /search/typeahead` / Meili) and `searchPodcastsGrouped` (parallel typeahead + hybrid → Matches / Also found). Concept search uses `searchSemanticGrouped` / `searchEpisodesSemantic` (`GET /search/semantic`: one CF embed → Qdrant podcasts + episodes; additive `feeds` + legacy `items`).
- `logic.mergeShowSearchResults` dedupes Meili vs hybrid by id / itunes / feed URL. Missing/generic typeahead genres are filled from matching hybrid results when their known genre agrees; title-only matches and conflicting genres are not enrichment evidence. Existing catalog identity, other metadata, order and grouping stay unchanged.
- `mapRegionForBriefing` maps content regions to briefing markets (`us` / `in` / `gb` / `global`; legacy `uk` → `gb`) via `ContentRegions.briefingMarket`.
- `SubscriptionRepository`, `ChapterRepository`, and `TranscriptRepository` expose catalog-adjacent data operations. `ChapterRepository` supports remote JSON, local file paths, and show note description parsing (`hasChaptersInDescription`, `parseChaptersFromDescription`). `TranscriptRepository` supports remote SRT/VTT and local file paths. Offline persistence and file retrieval for downloaded episodes are modularized in `ChapterOfflineStorage` (`saveOfflineChapters`, `getOfflineChapters`, `deleteOfflineChapters`, `hasOfflineChapters`) and `TranscriptOfflineStorage` (`saveOfflineTranscript`, `getOfflineTranscript`, `deleteOfflineTranscript`, `hasOfflineTranscript`). Normal `updateLatestEpisode` calls never replace a newer Room tip with an older item (`LatestEpisodeTipLogic`); same published date does **not** replace or badge. A successful full publisher-feed ingest passes `publisherFeedAuthoritative`, allowing the real feed tip to replace a newer PI cross-promo or same-date different identity. NEW is still set only when `publishedDate` is newer. Subscribe recovers a missing HTTPS `feedUrl` via `GET /podcast` (daily retry also runs in launch sync). For catalogue notification subscriptions, `SubscriptionRepository` writes RTDB `tracked_podcasts/{podcastIndexId}` with `title`, `imageUrl`, and an HTTPS `feedUrl` when a Room tip exists. Live RTDB rules allow those three keys only. The checker selects RSS whenever that URL is present, independently of Missing episodes?; it seeds `lastRssKey` quietly unless the newest RSS item matches a PI episode different from the saved `lastEpisodeId`. Turning catalogue notifications **off** removes the `feedUrl` child. Pure RSS uses the journaled per-device URL scopes described above. Unsubscribe sets a 14-day TTL on the local catalog (no CASCADE wipe), records an `unsubscribedAt` tombstone timestamp, and marks `isDirty = 1` for delta sync; resubscribing resets `unsubscribedAt = 0` and sets `isDirty = 1`. Show settings updates (notifications, custom genre/icon, auto-download, skip intro/outro, playback speed) mark the show `isDirty = 1` for cloud sync. `updateCustomGenre` applies user-defined genre overrides and custom icon keys for subscribed shows; unsubscription clears any custom tag/icon overrides and resets to original catalog genre.
- **Discovery on `/v2`.** While `RolloutSwitches.v2Discovery` is on (the default; read per request), `PodcastRepository` sends recommendations (`getPersonalizedRecommendations`), Home and Explore picks (`getHomeRecommendations`, `POST /v2/home/bootstrap` with a `V2BootstrapRequest`), the launch bootstrap (`getHomeBootstrapDataFast`), trending and its stream, semantic search, because-you-like, similar episodes, curated vibes, the curiosity deck and briefing metadata to the `/v2` routes; off sends each back to its v1 route. Show search (`searchPodcastsWithCorrection`, also the hybrid half of `searchPodcastsGrouped` and onboarding search) stays on v1 `/search` either way: shows carry no episode IDs, and `/v2/search` has no Apple or Podcast Index results, so shows outside the catalog would disappear. Typeahead, onboarding, content catalog v3, feedback, `/sync` and the OPML import lookup stay on v1 too. Answers have the v1 shapes:
  - **Episode IDs in.** Recipe IDs in answers are replaced by the stored ID that owns the episode on this phone (`DiscoveryEpisodeIds.localOwners`, before callers rank, dedupe or show them): recommendations, Home picks, semantic and similar episodes, because-you-like episodes, trending and vibe latest episodes, curiosity cards and briefing related episodes (bootstrap chapters and `ChapterRepository`, including a downloaded briefing's saved chapters file). The owner comes with the show its listener state is stored under (`DiscoveryEpisodeOwner`; the show's own feed for a show the listener switched to it), and the episode moves to that show; a curiosity card, which names its show by number, is then left as it is. Every translated or untranslated answer keeps the recipe ID it named in `Episode.recipeId`. With no trusted alias (most history older builds played from discovery, still unresolved), a unique listening-history or queue row of the same show with the answer's audio address is the owner, unless a trusted alias places that row elsewhere. An episode the phone can't place keeps its recipe ID, which resolves through `/v2/episode`. Show IDs never change.
  - **Episode IDs out.** Recommendation seeds and exclusions, and the similar-episodes seed, go as recipe IDs (`DiscoveryEpisodeIds.recipeIds`): a Podcast Index ID from an older build becomes its episode's recipe ID when a trusted alias has one, and phone-minted IDs with one (feed-only episodes, RSS episodes linked to a Podcast Index show) are no longer left out. A Podcast Index ID the phone can't place still seeds through its text fallback and is still excluded as itself (it can't clash with a recipe ID). `/v2` excludes by recipe ID only, so recommendations and Home picks also drop episodes the request's history holds after translation (`withoutHistory`), and similar episodes drop their own seed (`withoutSeed`, by stored ID or by show and title); the similar-episodes seed is `"0"` when the episode can't be placed. Recommendation bodies carry the normalised content languages (at most four; the API refuses more and expands `id` to `in` itself). Without a seed or an interest, personal recommendations make no request (as on v1), while Home and Explore picks ask for the country's default interests (`countryDefaultRecommendationRequest`, mirroring the Worker's `defaultInterests`), so a new listener gets popular picks as on v1. Home picks are marked fallback only for that request, as on v1 (interest-only picks are personal).
  - **Failures.** A failed `/v2` request never falls back to v1. It keeps the last good answer of the same request in this process (`V2DiscoveryLastGood`); recommendations and Home picks keep their last good picks per country across restarts (`RecommendationsLastGood`, translated again when read), including when an answer has no picks. With neither, the result is empty or null, and Home's bootstrap and picks are marked `failed` (`HomeBootstrapData.failed`, `HomeRecommendations.failed`) so Home and Explore keep the trending and picks they show (restored from their caches) instead of replacing them with an empty list. An empty success (a trending page past the end) stays empty.
  - **Caches.** `/v2` recommendation and because-you-like answers are cached under `v2|` keys, so a v1 answer never serves a v2 request or the reverse.
  - `RoomDiscoveryEpisodeIds` is the alias-table implementation (`episode_aliases`, trusted aliases only; a recipe ID two keys of one show share stays as it is; the audio-address match above); the app passes it as `discoveryEpisodeIds`. `DiscoveryRouting.install` gives the same switch and translator to code outside the repository: `BriefingLinks` builds the briefing chapters link on `/v2/briefings/chapters/<region>` while v2 discovery is on (the transcript link keeps `/briefings/transcript/<region>`, as the `/v2` briefing answer links it), and `ChapterRepository` translates related episodes of the chapters it fetches.
  - `RecommendationsV2Request` always sends `contractVersion: 2`, which the `/v2` recommendation bodies need. With the switch off, personal picks go straight to contract-1 `/recommendations` (`v1PersonalizedRecommendations`), exactly what shipped builds received: their v1 `recommendations/v2` request was always refused, so the switch restores the shipped behaviour.

- Cloud sync carries episode identity ([`docs/EPISODE_IDS.md`](../../docs/EPISODE_IDS.md) §5) through `sync.SyncEpisodeIdentity`, which `AppContainer` hands to `UserSyncCoordinator` and `QueueSyncResolver`. Every row keeps the ID it is stored under:
  - **Push.** A history or queue row carries its episode's `recipeId` and `catalogKey` only when its ID has a trusted alias under the row's own show. The recipe ID is left out when the alias table says it names another episode (another key of the show has it, or the local ID equal to it belongs to another show or key), so the server's removals by recipe ID and other devices never reach the wrong episode. A row whose own ID is in the recipe range but isn't its episode's recipe ID is sent without either field: the server compares such a row's key with the copy other devices stored and silently refuses a different one, while a write without a key is stored. The queue also sends its stored rich removals (an empty list too), with the same recipe ID rule.
  - **Pull.** Pulls send `richRemovals: true`. Before the resolvers merge anything, every pulled history and queue row whose ID has no alias gets one under its show: trusted when it names, by catalog key (else by a recipe ID exactly one key of the show has), an episode this phone already holds under a trusted ID, so it joins that episode's projected state; unresolved otherwise, so it is never a new owner and the show's next feed read can still attribute it. The idle mini-player is handed the pulled episode's owner ID, and `IdleSessionHandoff` in `:core:playback` leaves it alone when it already holds that episode under another ID. A pull from the start by a device that synced before (`executePull`'s `deliveredUntil`, the last sync time) doesn't restore a history row removed here: history removal is local, and a cloud row stored before the last sync that this device no longer has was removed by the listener.
  - **Queue merge.** `QueueSyncResolver` works per episode: a pulled item of an episode this phone queues keeps the phone's item and ID, each episode is queued once, and the playing episode keeps the ID it plays under. This phone's unsynced removals also drop the pulled item of the same episode under another ID, and the server's plain and rich removals (united; a rich removal counts only while the plain list still holds its ID) also drop this phone's unsynced item of the same episode. A removal whose episode the same side still queues under another ID is stale and matches only its own ID; a pulled item counts by the identity it carries too, so the cloud's re-queue under an ID this phone can't identify yet still makes the cloud's removal stale. The stored rich list stays in step with the plain one: without unsynced changes here it is the server's own list (not merged with this phone's older one), and no stored rich removal names an episode the merged queue holds, by this phone's aliases or by a pulled item's identity, because the server removes every queue row of a rich removal's episode. The merge keeps one entry per episode, so the cloud can still hold an episode under an ID this phone folded into its own entry; a removal on this phone therefore records every ID of the episode (`QueueRepository` through `EpisodeListenerStore.queueRemovalIds`), which also reaches a copy an older build pushed without identity. `QueueItemHydration` builds the row of a pulled item this phone doesn't queue: the catalog and history tiers read the episode under any of its trusted IDs, and the network tier asks `/v2/episode` (through `PodcastRepository.getEpisode` with the show) for the recipe ID the server sent before the stored ID.
  - **One-time catch-up.** Sync metadata version 3 (`UserSyncCoordinator.IDENTITY_SYNC_METADATA_VERSION`): the first sync pulls from the start, then pushes back the cloud copies that lack an identity this phone knows (`identityCatchUp` in `SyncIdentityCatchUp.kt`): each pulled history row exactly as the cloud sent it, with its own `updatedAt`, plus only the missing recipe ID or catalog key, and the pulled queue the same way (without rich removals, so the server keeps its list) when one of its items gains an identity. The server keeps every other value, other devices' delta pulls receive nothing, and no local row is marked for the push. A copy that names another key or recipe ID, or a row this phone can't identify, is left as it is. The pushes go batch after batch in the same sync (at most `MAX_CATCH_UP_PUSHES`, 100 batches of 100 rows), and version 3 is recorded only after all of them went through; a failed or cut-short run starts again with a pull from the start on the next sync, and copies already caught up are skipped.
  - `requestIdentityCatchUp()` sets the version back below 3 on a phone that already caught up (under the sync lock, so a running sync can't record the catch-up done over it); the feed address repair calls it once every followed show was read again, so episodes those reads settled get their identity in the cloud.
  - The account-switch purge also clears the queue's rich removals, and the switch sets the sync metadata version below 3 and runs the catch-up for the new account right after its pull from the start. Cloud sync doesn't carry the link of an RSS show to the Podcast Index show it replaced yet, so a phone restored from the cloud links no switched show.

Release keeps only the JSON backup/cache model contracts used reflectively, rather than the full catalog package. The artifact gate follows nested backup and recent-intent models from compiled classes to reject field renaming, missing defaults and erased TypeToken signatures.
