# `:core:playback`

## Purpose

Owns playback session control, queue orchestration, smart queue logic, Media3 playback services, the offline download foreground service, and Android Auto browse/collage support. It does not own Room schemas, preference storage, RSS parsing, ranking persistence, smart-download workers, or feature UI.

## Public API

- Queue metadata additively carries available episode/show artwork sources while preserving media IDs, audio cache keys and queue provenance. The service bitmap loader tries the active item’s alternatives, times out each fetch after eight seconds and admits one transient recovery attempt. The source lookup runs on the player’s main dispatcher; bitmap fetching remains on IO. `RecoveringBitmapLoader` retains one successful/in-flight request and expires failed results after 30 seconds instead of pinning a failed Media3 future forever; cancelled work is immediately retryable. JVM tests cover cooldowns, byte-array ownership, cancellation and fallback ordering.

- `QueueManager.playContextEpisodes` starts a fresh New Episodes queue from the visible list snapshot. It persists the ordered suffix atomically, preserving each episode’s show metadata and opaque IDs. The `library_latest_episodes` source survives Room restore, Android Auto, and Cast metadata; Smart Queue waits until the final context episode completes before requesting fallback candidates. Completion is persisted before that refill, and paused/sleeping/replaced sessions cannot be restarted by a delayed result. Cast context provenance is serialized in receiver custom data because Media3 drops extras; remote continuation requires the receiver’s explicit finished idle reason and waits for insertion acknowledgment. The refill cap counts current/upcoming items rather than the consumed prefix of a long list.
- `PlaybackActivationRequest` carries a one-shot transport position, including an intentional zero. `PlaybackIntroOutroController` uses saved history for automatic activations even when Media3 has already advanced the clock by a few milliseconds. Policy-selected zero restarts still apply intro trim; explicit positions and route transfers retain their chosen position.
- A different episode activation discards abandoned transport positions; same-item seeks and live Android Auto resumption do not leave positions pending for later replay. Guarded refills accept the triggering episode's consumed-prefix trim in Room while rejecting replacement, reordering, or upcoming-row edits. Context fallback advancement carries the same service-owned natural-completion signal as outro advancement, with bounded cleanup for absent controller callbacks.

- `PlaybackRepository` exposes player/session operations to app and feature UI (history ports via
  class delegation to `PlaybackHistoryStore`; queue / transport / sleep / history helpers via
  same-package extension API files), and implements `:core:catalog:ports` `ActivePlaybackSyncPort` (`getActivePlayingEpisodeId`, `stopAndClearActiveSession`) to shield the current active track from remote overwrite during cloud sync and ensure active playback and in-memory queue teardown on account switches. `isTransportReady()` reports whether a Media3 controller is connected; the transport API also exposes previous/next and seek (skip forward/back) operations used by the home-screen widget adapter. `PlaybackChaptersTranscriptController` resolves chapters and transcripts during playback with offline fallbacks (local disk files, cached/downloaded transcripts, and show notes description timestamp parsing).
- `QueueRepository` and `QueueManager` persist and orchestrate explicit queue operations. `QueueRepository` implements `:core:catalog:ports` `QueueSyncPort` (`getQueueSnapshot`, `getQueueMetadata`, `applyRemoteQueueState`, `markQueueSynced`). `QueueRepository` mutation methods (`addToQueue`, `clearQueue`, `replaceQueue`, `reorderQueue`, `removeFromQueue`) execute atomically within Room transactions and call `QueueDao.bumpQueueVersion`, advancing a monotonic `queueSequence` version number, recording current device ID, marking `isDirty = 1`, and logging removed episode IDs in `recentRemovedEpisodeIds` tombstones to guarantee consistent, order-preserving sync across devices. Domain episode snapshot is accessible via `getQueueEpisodeSnapshot(): List<Episode>`. `replaceQueue` keeps the release date the queue knew for an episode queued again without one (played from a history row), so its listening still counts as new or older. `QueueManager.playEpisode` preserves `preferredSort` on the active podcast and passes `contextSourceId` to `queueRepository.addToQueue`. `QueueManager` emits `queue_modified` add only after `PlaybackRepository.addToQueue` returns success.
- Every queue entry plays under its own show (`QueueShowPolicy`). Add to queue, Play next and same-show continuation fill an entry's missing show ID, title, host, genre and artwork from the show it was queued from; an episode that already names another show keeps its own fields, so two shows never mix. Smart Queue refill items carry their show ID in the `boxlore_podcast_id` media item extra, so an entry the UI rebuilds from the player (`buildEpisodeFromMediaItem`, and the transition's recovery when no entry exists) keeps it. A rebuilt entry takes its show title from the item's album title, then its subtitle, then its artist (`QueueShowPolicy.showTitle`): Android Auto subtitles add the duration and Smart Queue artists are the host.
  - A new queue (`playQueue`) gives its episodes without a show of their own the show it was started from, in the saved queue too, so they keep it after a restart; episodes of another show keep theirs. Reloading the current queue (`replayQueue`, used by `playFromQueueIndex` and an emptied player) relabels nothing. A queue whose first episode names another show (Downloads "Play all" under All Downloads, a Home mix) starts under that episode's show (`QueueShowPolicy.startShow`), so the session saved for it never takes the placeholder's name. The "unknown" show ID an episode page uses for a show it doesn't know counts as no show, and nothing is copied from a show without a real ID.
  - When an item becomes current, `PlaybackMediaControllerBridge` takes the show from the episode: Room's copy of that show, else the previous show only when it has the same ID (or the same title, for an entry without an ID), else the episode's own fields. An entry with no show at all plays under "Unknown Podcast", never another show's name. The current entry's show is written back to the saved queue, so a restart restores it. A transition whose item is no longer current once its lookups finish leaves the state to the newer transition.
- The queue holds at most `PlaybackRepository.QUEUE_LIMIT` (50) episodes; `addToQueue` returns false past it or for an episode already queued, and screens read the constant to say which.
- `PlaybackQueueCoordinator` emits `queue_modified` remove on remove; `undoQueueRemoval` emits a compensating `add` (`source=undo`) so undone removals do not permanently skew analytics. Removal also notifies `QueueRepository.removeFromQueue` to update metadata tombstones.
- `QueueMath`, `QueueSkipMemory`, `SmartQueueEngine`, `SmartQueueSources`, and `MixtapeEngine` implement queue and mixtape logic. `SmartQueueEngine.SHOW_BINGE_SOURCES` allows deep same-show continuation on show pages and same-show refills while guarding discovery recommendation landings. Smart Queue refill and same-show continuation (`SameShowContinuationLogic.computeCandidates`) skip trailers by `Episode.isTrailer`, so an episode the feed tags as a trailer but that runs longer than 15 minutes is queued as a full episode (`SmartQueueEngineTest`, `SameShowContinuationLogicTest`). `SmartQueueEngine.resolveGenre` checks `PodcastGenres.canonicalize(currentPodcast.customGenre) ?: currentPodcast.genre` so custom show genres adapt refill categories. `DefaultSmartQueueSources` passes `preferredSort` and reads a bounded `getEpisodeWindow` (~200, around the current episode for same-show continuation) — never `getAllNewest` of a mega-feed. Ready local catalogs serve Room pages; not-ready PI shows still union cached extras. Settings → Playback → **Smart queue** (default on) is today’s mixed refill. Turning it off makes refill return same-show continuation only and skip resume/subscription/rec/trending fill. Turning it back on from the queue sheet (empty-state **Turn on**) writes the pref and the playback service refills if the queue is already low.
- `SameShowContinuationCoordinator` and `SameShowContinuationLogic` coordinate optional continuation offers when recommendation or discovery origin playback skipped same-show binge fill. When forward-in-time episodes exist and are not already queued, `PlayerState.sameShowContinuation` exposes `visible = true` and `availableCount` (capped at 5). `PlaybackRepository.addSameShowContinuationEpisodes()` inserts candidate episodes immediately behind the active track tagged with `SOURCE_SAME_PODCAST`.
- **One episode, several stored IDs** ([`docs/EPISODE_IDS.md`](../../docs/EPISODE_IDS.md) §5). Playback reads and writes listener state through `:core:database`'s `EpisodeListenerStore`; an episode stored under one ID (every show today) behaves exactly as before.
  - The media ID stays the one playback started with. Progress, completion and replays from `PlaybackProgressCoordinator`, `PlaybackServiceHistory`, Android Auto and `PlaybackHistoryStore` go to the episode's owner row (`historyId`); completions and replays also reach the episode's other trusted IDs and its group settings (`recordCompletion`). The listen time the service refreshes when an item starts playing goes to the owner too.
  - Everything that decides where an item starts reads the episode's projected state, whichever ID is playing: `PlaybackIntroOutroController` (resume and skip-beginning for queue auto-advance, Smart Queue and Android Auto starts), `PlaybackRepository.checkSavedProgress`, `PlaybackTelemetrySession`'s replay flag, and session restore (`PlaybackSessionRestoreHelper`, used by app start, the controller sync and the idle cloud session). A newer cloud session never replaces the idle mini-player's episode with the same episode under another of its IDs (`IdleSessionHandoff`): cloud sync hands over the episode's owner ID, which may differ from the ID the player holds. A restore keeps the media ID; when no ID of the episode has a row it creates one under the owner, never an unplayed row beside the episode's real state. Android Auto resumption and voice search read `EpisodeListenerStore.lastPlayedSession`.
  - Like, mark played and mark unplayed work out an absolute target from the projected state and write it to every trusted ID (`toggleLike`, `toggleCompletion`, `markEpisodeAsCompleted`, bulk mark played/unplayed). Bulk mark played/unplayed works out owners and group settings in batches (`EpisodeListenerStore.historyIds`, `recordCompletions`). Android Auto's like toggle keeps its old single-row write for an episode with one ID. A seek saved from an episode page (`savePlaybackState`) of an episode stored under several IDs writes the owner's row and keeps that row's like, show and episode metadata as stored.
  - The owner row stays under its own show. A history row created for the owner while another ID plays (the like and mark-played buttons, the progress seed in `ensureCurrentHistoryRow` and `PlaybackProgressCoordinator`, natural and manual completions in `PlaybackServiceHistory`, Android Auto, session restore) takes the owner's show through `EpisodeListenerStore.ownerRow`, never the show playing it, so a show switched to its RSS feed writes progress to the Podcast Index show's row under that show (decision D8).
  - Listening insights (`observeInsights`) read every history row (`ListeningHistoryDao.observeAllStoredHistory`, paged, without descriptions, projected by `EpisodeListenerStore.projectedCompleteRows` from those rows alone), not the screens' latest 300, so finished, in-progress and liked counts and history-based estimates cover the whole history. By show, they count the history, sessions and daily totals of a Podcast Index show the listener switched to its RSS feed as the RSS show's (`EpisodeListenerStore.showReplacementsFlow`). `PlaybackRepository.episodeGroupTokens`, `episodeAliasGroups` and `withEpisodeAliases` let screens find an episode under the ID they list.
  - Sessions stay whole for 400 days (`ListeningSessionRecordLogic.RETENTION_DAYS`, 180 before 2026-10-31), so a calendar year keeps each play's times, output, source and release date for a year in review; older sessions fold into daily rollups.
- Listening history's screen (`:feature:history`) reads the whole history (`observeFullHistoryTimeline`: every stored row, projected the same way, without manual or bulk completions, newest play first, a switched show's rows under its RSS id), every phone's timed listening per day, show and episode (`observeListeningByDay`: sessions added up per day, episode and show by the database (`ListeningSessionDao.observeSessionDays`), and daily rollups, of every origin through `ListeningDayLogic`, an episode stored under several trusted IDs counted once under one of them (`EpisodeListenerStore.countedIdsFlow`), with listening by part of the day, the longest sitting (a summary's own, Room v41, else its one session's; not known when a part without one could hide a longer sitting, `ListeningDayTotals.longestOf`), and time by output, by source, of new releases and with a known release date (Room v42; a part from before v42 adds no new releases to one that knows its dates, `ListeningDayTotals.newReleaseOf`), under a switched show's RSS id), and the shows played with their genres (`observePlayedShows`; a switched show's Podcast Index row joins its RSS show's, so rows, time and genres meet under one show). Whole-history reads wait for writes to settle and run at most once a second (`throttleLatest`), so playback ticks don't rebuild the screen. `HistoryBeyondScreenLimitTest` covers rows beyond the screens' 300 and the per-day listening.
  - History, resume, liked and completed lists, the player's like state, saved positions, recommendation seeds, Smart Queue sources, Android Auto browse lists, voice search and artwork prewarming read projected rows, so an episode counts once. Screens that look an episode up by the ID they show read `PlaybackRepository.likedEpisodeIds` and `historyForEpisodeLookup`, which list the episode under each of its IDs.
  - Removing an episode from history removes its rows under every ID and its group settings; Undo puts every row back exactly as stored, with the settings (`ListeningHistoryRemoval.rows`, `groupState`). Clearing history clears every episode's group settings.
  - Media items read the bytes of whichever ID holds the completed download: `PlaybackQueueCoordinator`, `PlaybackTransportHelper`, `AutoMediaResolver` and Smart Queue refill set `customCacheKey` from `EpisodeListenerStore.downloadHolders` (the download's own key, `EpisodeMediaCacheKey.of`). No file or ID is renamed.
  - The queue holds an episode once: adding it under another of its IDs is a duplicate. A removal deletes the removed ID's row and the row of each other trusted ID that is queued, except the one that is playing, which stays in Room as it stays in the player (`QueueAliasPolicy`, `QueueRepository.removeFromQueue`). Both removal lists record every ID of the removed episode (`EpisodeListenerStore.queueRemovalIds`), queued here or not: a cloud sync pull keeps one queue entry per episode, so the cloud can still hold the episode under another ID, and only a removal by ID reaches a copy an older build pushed without the episode's identity. While the episode stays queued under the playing ID, only the removed rows are recorded. `clearQueue` and `replaceQueue` record the same way for each episode that leaves the queue. The rich list (`queue_metadata.recentRemovedEpisodes`) records each ID with the show, catalog key and recipe ID. Queueing the episode again under any ID (an add or an Undo) clears the removals of every one of its IDs from both lists. A pulled queue state keeps only rich removals that the pulled plain list still holds and whose episode isn't queued again (`applyRemoteQueueState`).
  - `SmartQueueRefillCoordinator` excludes every ID of each queued episode, keeps one pick per episode and now sets each pick's `customCacheKey` through `PlaybackMediaIdPolicy.customCacheKey`, so a downloaded pick plays from its file. Refill stays service-owned.
- `PlaybackMediaIdPolicy`, `PlaybackArtworkResolver`, and `PlaybackSkipPolicy` define session IDs, artwork, and skip behavior.
- A briefing episode that reaches the player without its chapters or transcript link (`PlaybackChaptersTranscriptController`, `PlaybackMediaControllerBridge`) gets them from `:core:catalog` `BriefingLinks`: chapters on `/v2/briefings/chapters/<region>` while v2 discovery is on, so related episodes come under recipe IDs and are shown under this phone's own IDs, and the transcript on `/briefings/transcript/<region>`. Links the briefing answer carries (signed) are always kept. Briefing episode IDs stay `briefing_*`.
- `PlaybackMediaIdPolicy.customCacheKey` (via `:core:model` `EpisodeMediaCacheKey`) appends briefing audio `v=` so Media3 does not keep playing a same-day regenerated brief from a stale SimpleCache entry.
- `PlaybackSkipPolicy` also owns intent-aware stale resume: when Settings → Playback → **Restart forgotten episodes** is on (default), implicit plays (queue / mixtape / Smart Queue / casual) soft-expire mid-episode seek after 7 days without `lastPlayedAt`; Jump Back In (`home_hero_resume*`) and History (`library_history`) always seek. Progress is never wiped — seek policy only. Mixtape/SQ still *select* unfinished episodes within the 30-day suggestion band; chrome follows soft-expire (mixtape hides progress / “Xm left”; Smart Queue stamps `resume_stale` → queue label “Starting over”).
- `PlaybackControlSync` keeps UI playback speed / seek sizes aligned with Media3 when a session is cleared or a new queue starts, and sanitizes user-requested speeds before apply/persist.
- `BoxLorePlaybackService` owns one Media3 `CastPlayer` over the existing local `ExoPlayer`. Queue, position, speed, sleep timer, intro/outro policy, completion persistence, smart refill, notification, widgets, and Android Auto therefore follow the active local or Cast route without constructing a second playback graph. Smart Queue submits each refill as one playlist mutation so asynchronous Cast queue sequence numbers cannot race; reconciliation preserves the complete app queue during a brief partial transfer snapshot, then accepts a stable receiver subset after unsupported local-only items are sanitized. Metadata-less remote transitions retry when matching Cast metadata arrives instead of inventing placeholder or “Unknown Episode” records. `PlaybackServicePlayerFactory` and `BoxLorePlaybackService` guard session activity `PendingIntent` creation and `assembleSession` with `try-catch (e: SecurityException)`: if the system PendingIntent UID cap is hit on older devices, session assembly logs the failure and falls back gracefully with initialized command buttons, allowing `onGetSession` to return `null` safely without crashing or throwing `UninitializedPropertyAccessException`.
- `PlaybackThreadPolicy` enforces Media3 `MediaController` thread affinity (Main Looper). `PlaybackRepository.restoreLastSession` executes within `withContext(PlaybackThreadPolicy.mainDispatcher)` to guarantee thread safety during cold startup or background widget sync, and transport APIs hop background invocations to the main dispatcher or gracefully fall back.
- `PlaybackRouteState` mirrors remote-device name/volume into `PlayerState`; `PlaybackRepository.setOutputVolume` controls the active route. Cast-framework lifecycle sync treats asynchronous process restore as an undecided route, refreshes Media3 after reconnect, and rejects stale remote `DeviceInfo` only once an ended or failed session remains disconnected past the recovery grace period. `PlaybackRepository.stopCasting` clears that route immediately while stopping remote playback before terminating the receiver session, preventing hidden TV audio even while Media3's route flag is briefly stale. `BoxLoreCastTransferCallback` removes receiver placeholders without playback URIs before a remote-to-local transfer, preventing ExoPlayer crashes during disconnect. `CastMediaEligibility` admits public HTTP(S) sources and rejects local/private IP literals; `BoxLoreCastMediaItemConverter` validates every effective receiver URL, replaces device-local download URIs with their original stream URL, and keeps that internal URL out of analytics context.
- `HistoryRecommendationLogic`, `AutoVoiceSearchLogic`, `SmartQueueRefillPolicy`, `MixtapeResumePolicy`, `PlaybackEntryPointResolve`, `NightWindowLogic`, and `ListeningHistoryUpsertLogic` are JVM-testable playback helpers. `PlaybackControllerStatePolicy` keeps an empty/unprepared MediaController from erasing Room-restored progress while preserving policy-selected zero-position restarts, `PlaybackProgressPersistencePolicy` rejects out-of-order asynchronous snapshots while preserving intentional restarts/backward seeks and determining when `lastPlayedAt` must update on short plays or intentional replays, `PlaybackHistorySeedPolicy` resolves ordered non-blank service metadata into missing history rows with fallback enrichment from podcast and catalog repositories, `PlaybackSessionRestoreHelper` coordinates cold-start and controller session restoration without reverting to unrelated sessions while healing blank podcast metadata into Room, and `PlaybackTaskRemovalPolicy` requires a final save before stopping an inactive service. `PlaybackEntryPointResolve` maps fine-grained source-context `entry_point` strings (`home_mixtape`, `learn`/`learn_history`, `briefing`) to coarse `PlaybackEntryPoint` for queue/mixtape policy while the raw string still attributes `playback_*`.
- `AutoMediaResolver` and `AutoMediaResolutionPolicy` resolve playable items and metadata for Android Auto, enriching missing fields independently while preserving local non-blank metadata and falling back to catalog sources. An item or saved browse item under an old ID of an episode stored under several trusted IDs reads the episode's projected history and its queue row under any of its IDs, also on the path where the item already carries a URI; `resolveDomainEpisode` returns the queued copy under any of the episode's IDs (so resumption lines up with the queue), else the episode under the ID asked for. The catalog fallback (`PodcastRepository.getEpisode`) resolves old IDs through aliases too.
- `AutoPlaybackResumptionPolicy` and `AutoPlaybackResumptionHandler` coordinate Android Auto and media button reconnection playback resumption (`onPlaybackResumption`), managing live player continuation, active miniplayer restoration, dismissed/inactive incomplete episode resumption, and playlist queue alignment.
- `AutoBrowseControllerMatcher` filters MediaSession controllers using Media3 companion/automotive inspection APIs and known automotive package identifiers (`com.google.android.projection.gearhead`, `com.google.android.apps.automotive.media`, `com.android.car.media`) so Android Auto connection and browsing analytics are strictly isolated from standard Bluetooth AVRCP (`com.android.bluetooth`) and system notifications.
- `android_auto_connected` / `android_auto_disconnected` count only real car connections: an Auto controller while the phone is in car mode or on Android Automotive (`CarConnectionState`). Android Auto's app also connects in the background without a car, which used to count.
- `AutoArtworkFetchLogic`, `AutoCollageFreshnessLogic`, and `AutoArtworkPipeLogic` encode Android Auto artwork fetch, cache policy, and safe pipe streaming for hermetic tests.
- `AutoCollagePrewarmPolicy` and `AutoCollageFolderLogic` encode prewarm throttle and aligned image/key folder inputs for hermetic tests.
- `PlaybackIntroOutroController` manages intro-skip and outro-trim playback lifecycle. Natural completion remains event-driven; ending-trim polling runs only during active playback with a real trim, clears completed monitor jobs, and uses a 500 ms cadence.
- `service.BoxLorePlaybackService`, `service.MediaDownloadService`, and `service.AutoCollageProvider` are manifest-facing services. `MediaDownloadService` returns `null` for `getScheduler()` on Android 12+ (API 31+) to comply with Media3 background restrictions, and guards `onStartCommand` with exception handling that terminates cleanly via `stopSelf()` with `START_NOT_STICKY` if invoked in an invalid background state. The download foreground notification refreshes at a five-second cadence to avoid per-second notification wakeups while retaining useful progress.
- `service.SmartQueueRefillCoordinator`, `service.CoilBitmapLoader`, and `service.auto.*` support service internals and Android Auto.
- Android Auto browse artwork:
  - `AutoArtworkRepository` + `AutoArtworkSourceStore` register remote/local sources into an in-memory map immediately and `commit` prefs on a background thread before/while returning `content://…/art|local|collage/…` URIs.
  - Those `.collage` links are display-only. Every place playback saves artwork (progress and completion history rows, the controller bridge, queue items built from player items, restored sessions, Smart Queue seeds) uses `PlaybackArtworkMetadata.savedArtworkUrl`: the item's first real `boxlore_artwork_sources` entry, else its artwork when that is not a `.collage` link. `AutoMediaResolver` keeps each cover's original address in those sources (`withOriginal`) when it swaps the artwork: ahead of them for an episode's own cover, after them for a show-only fallback, so an item that already carries its episode cover keeps saving it. It skips `.collage` links already saved in history, queue or download rows and in the incoming item, so an item whose only artwork is such a link still gets a catalogue cover. `PlaybackArtworkMetadataTest` covers saving, ordering and that lookup.
  - `AutoCollageProvider` lazily fetches remote covers with validated HTTPS redirects, lenient image content-types, magic-byte checks, and one retry; folder collage URIs include a `v=` cache-buster so Auto hosts reload when resume/history content changes.
  - `AutoCollagePrewarmer` / `AutoCollageGenerator` / `AutoCollageLayouts` rebuild section collages from content keys (resume episode IDs, queue IDs, subscriptions, …), use a shorter TTL for partial/fallback tiles, and refresh on mark-complete / queue changes via `AutoBrowseLibraryHost.requestAutoCollageRefresh`. MIX/RESUME badge labels prefer app-merged Google Sans Flex with lettering roundness from `boxlore_theme_fast_cache` via `:core:prefs` `FontRoundnessAxis` (no `:core:designsystem` dependency).
  - Branded fallback tiles keep uppercase section labels (`PLAY`, `LIBRARY`, …), but the generic tile spells the product name `boxlore` in lowercase. The browse root title comes from `:core:catalog`'s `auto_app_name`.
  - `AutoArtworkDownloader` is the shared HTTPS fetch path (validated redirects + public-host checks) used by both collage generation and the ContentProvider.

`PlaybackRepository` implements `ListeningHistoryPort` / `ListeningHistoryBackupPort` via Kotlin
class delegation to `PlaybackHistoryStore`. Same-package extension files expose the remaining

## Dependencies

- Project dependencies: `:core:model`, `:core:network`, `:core:database`, `:core:catalog`, `:core:downloads`, `:core:ranking`, `:core:analytics`, and `:core:prefs`.
- Libraries: Media3 ExoPlayer/Session/UI/Cast, Google Cast framework, Coil, Palette, Gson, OkHttp, coroutines, and AndroidX core.

## Artwork decoding

`CoilBitmapLoader` dispatches both byte-array decoding and URI artwork loading to IO in the service scope. Media3 callers receive a cancellable future immediately; decode errors complete that future exceptionally. Notification covers request at most 512×512 pixels and software bitmaps. `CoilBitmapLoaderTest` covers asynchronous decoding, invalid data and service cancellation.

- Release runtime dependency snapshots include Jsoup through `:core:catalog`, which owns shared show-notes resource and chapter parsing. No direct parser-library dependency is added here.

## Threading / lifecycle

- `PlaybackRepository`, `QueueRepository`, and `QueueManager` are application-scoped through `AppContainer`.
- **One record per listen** (`PlaybackTelemetrySession`):
  - A listen runs from sound starting until it pauses, finishes, switches episode, stops or the service closes (`end` takes the reason). `ListenEndRule` decides: rebuffering keeps the listen open; a pause, a suppression, the end or a stop ends it, also when it happens during rebuffering (no second `onIsPlayingChanged` comes then, so the service ends it from the pause, suppression or state callback).
  - `ListenTally` counts it on an injectable clock: `sampledMs` from the once-a-second ticker, exactly as the local listening record and ranking always counted (they still use it), and `heardMs` for the listen record, which adds the audio between the last sample and a jump or the end. It also counts the listener's seeks each way (not intro or outro skips, not moves to another item), buffering spells, where the listen left its episode when the player moved on (its `end_position_seconds`), and the wait from the first play request of a press to sound (`onPlayWhenReadyChanged`, and `onPlaybackResumption` before a resumed session resolves).
  - Plays asked from boxlore's screens carry `screen` and `previous_screen` (`PendingEntryPoint.withScreens` in `PlaybackRepository` and `PlaybackTransportHelper`).
  - What asked to play (`controlled_by`): the session's `ForwardingPlayer` reports `play` and `setPlayWhenReady(true)`, and the service reads `MediaSession.controllerForCurrentRequest` (`PlaybackControllerKind`: app, car, notification or system media controls, other). Media3 hands media buttons to the player as its notification controller, so `onMediaButtonEvent` records the real sender first and that wins for the play it causes. Requests the service makes itself change nothing, so a listen that follows another keeps its controller.
  - `output` comes from `ListeningOutputRoute.forAnalytics` at the end of the listen (the car is a controller, so car mode reads the audio route; hearing aids count as Bluetooth). `playback_mode` is looked up as soon as the listen starts (download when any stored ID holds a finished download), is unknown if the listen ends first, and is stream on Cast.
  - `playback_session_ended` goes out once per listen; `playback_paused` is still built but off by default. Only buffering of 5 seconds or more is sent alone as `playback_buffering`.
  - Errors go out once per cause per episode until a listen starts (`PlaybackErrorOnce`, which remembers every episode tried since), also to error tracking with links and tokens removed.
  - `ListenNoteKeeper` writes a note when a listen starts and every 30 seconds while it plays (`boxlore_listen_note`), and clears it when the listen ends; `ListenInterruptions.reportLeftover`, called once at app start, sends `playback_interrupted` for a note Android's ending of the app left behind and clears it.
- Each timed play (`PlaybackTelemetrySession`, saved through `ListeningSessionRecordLogic`) also records its listening time (`wallMs`: each natural position advance divided by the playback speed, `ListeningSessionRecordLogic.listenedWallMs`, so buffering and pauses never count), how it started (`playSource`: a Lore or Smart Queue queue context, else the analytics glossary's canonical entry point), where it was heard (`service.ListeningOutputRoute`, set on the session by the service as `listeningOutput`: Cast, the car, Bluetooth, wired or USB headphones or the speaker; Android 13+ reads the media route, older versions the connected outputs in Android's routing order) and the episode's release date (queue, then catalog; seconds or ms stored as ms, `releaseDateMs`). A recorded play adds its show to the played shows (`PlayedShowDao.recordPlay`, with the art of the episode's history row). A progress save from playback dates the first play and a finish by listening (`ListeningHistoryUpsertLogic.buildProgressSaveEntity`); the database keeps earlier dates, and only playback dates a finish. Sessions carry the listening device ID the service sets (`listeningDeviceId`, from `BoxcastPrefs.getOrCreateListeningDeviceId`). Undo of a history removal puts back the dates and the sessions' and daily summaries' new fields, the summaries' richer totals included, their time with a known release date (Room v42) too (`PlaybackHistoryMappings`). `ListeningHistoryItem` carries `firstPlayedAt` and `finishedAt`. `PlaybackFinishes.lastAtMs` is when the player on this phone last played an episode to the end in this run (both play-to-end paths set it before the row is written); a replay sets it again though the row keeps its first `finishedAt`, and marking played, sync and restores never set it. Home uses it for the NPS survey and the review prompt (`PlaybackFinishesTest`).
- `PlaybackRepository` polls MediaController position only while app UI is foregrounded; the playback service is the sole owner of active-session progress persistence and telemetry. Service writes capture live Player state before a playlist can be cleared and serialize sequence-stamped snapshots through one coordinator, so an older suspended write cannot replace a later seek/restart. Replayed completed episodes reset completion via `reopenProgress` when intentional progress occurs, and `ensureCurrentHistoryRow` refreshes `lastPlayedAt` immediately on play initiation so quick plays (<10s) are discoverable on cold restart. Service-only entry points such as Android Auto atomically seed missing history rows. When the UI returns to an empty player, it refreshes from Room instead of replacing a valid restored duration with `TIME_UNSET`/zero. This adds no background UI polling or duplicate periodic Room writes.
- `BoxLorePlaybackService` is a Media3 `MediaLibraryService`; it resolves shared dependencies lazily after application startup and keeps its local and remote players service-scoped so transfers continue while the Activity is absent. A local session that stays paused and backgrounded for 15 minutes saves progress, rechecks eligibility after persistence, and stops the service; resumed playback, cancellation, buffering intent, foreground UI, and Cast sessions bypass that teardown.
- The local ExoPlayer opportunistically enables platform audio offload only when the device can preserve playback-speed behavior. `WAKE_MODE_NETWORK` remains enabled for reliable screen-off streaming.
- Player callbacks run on the main thread; database, artwork, and recommendation work use coroutine scopes and background dispatchers.
- Playback errors go through `PlaybackErrorSkipGuard`: a failed episode is skipped and the next one starts only while the listener wants playback. After three failures in a row with nothing playing in between (offline, CDN outage), skipping stops and the player pauses on the failed episode with the queue kept, instead of looping while Smart Queue refills. A paused listener is never resumed by an error (the toast then says the episode couldn't play and the next one is ready, not "skipping"), a successful episode or any new listener-started queue resets the count (`PlaybackQueueCoordinator.playQueue` calls its `onQueueStarted` hook, which every play, play-episode, play-from-queue and skip-to-episode path goes through), and resuming an idle player after an error prepares it again. Smart Queue refill never appends episodes without an audio URL.
- The MediaController connection future can fail when the session rejects the controller (for example while the service rebuilds its session). `PlaybackMediaControllerHandle.awaitController()` returns null instead of throwing and asks `PlaybackRepository` to reconnect, at most three times with growing delays (`MediaControllerReconnectPolicy`).
- Artwork and audio URLs that are null or blank never reach `Uri.parse` (`PlaybackUris`); catalog models declared non-null can still carry null from Gson.
- "Play next" on an episode already in the queue moves it after the current item instead of adding a second copy (`QueueMath.placeNext`).
- `BoxLorePlaybackService` stops itself instead of crashing when the player cannot be created, as on ROMs that report API 34 without the API 34 framework methods Media3 calls.

## Persistence & identity

- Manifest-facing service class names are system identities.
- Media ID prefixes such as `episode:`, `queue:`, and `learn:` are session and Android Auto contracts.
- SharedPreferences file `boxcast_player` stores playback session flags.
- SharedPreferences file `boxlore_listen_note` holds the note of the listen in progress (`PrefsListenNoteStore`); it is empty between listens and left out of backups and device transfers, so a restore never reports a listen again.
- SharedPreferences file `boxlore_install_milestones` holds `first_play_claimed` (`FirstPlayClaim`, `PrefsFirstPlayStore`): `first_episode_played` is claimed once per install when a listen starts, whatever started it, with the episode and show. The file is left out of backups and device transfers, so a restored or new phone counts its own first play; an install updated from an older build that already sent it from the screen stays quiet. The claim is taken when the listen starts (on the main-thread scope, in start order), not after the show lookups, so the first play is the one that started first; it's a ticket that is saved only once the event is sent, so a listen whose lookups fail or are cancelled hands it to a later one; the app's first launch notes once whether the install came from an older build (`FirstPlayInstallOrigin.note`, `updated_from_older_build`), so updating a restored phone before its first listen can't hide it (`FirstPlayClaimTest`).
- SharedPreferences file `android_auto_artwork_sources` maps Android Auto artwork content keys to remote HTTPS URLs or sandboxed local paths (identity for Auto collage ContentProvider; do not rename lightly).
- Preference key `device_uuid` is a stable install identifier and must not be logged raw.
- Queue, history, and download rows are persisted by `:core:database` and `:core:downloads`.
- `customCacheKey` stays the episode ID (`EpisodeMediaCacheKey`); an item of an episode stored under several IDs uses the key of the ID that holds its download, which is that ID. Media IDs are never translated to another ID mid-playback.

Media-session bitmap loading classifies transient transport failures separately from decoding failures and preserves cancellation across fallback attempts.
