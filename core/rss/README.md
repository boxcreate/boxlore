# `:core:rss`

## Purpose

Owns RSS feed fetching, parsing, deterministic ID generation, episode catalog management, freshness checks, and the RSS subscription port implementation. It does not own Podcast Index HTTP APIs, download management, playback services, ranking persistence, or feature UI.

## Public API

Failed automatic fetches record a six-hour retry boundary while keeping catalogs stale and retaining last-good rows; manual refresh and release pushes bypass it.

- `RssEpisodeCatalog` adapts true RSS subscriptions to the same refresh/read contract as catalog shows, using `rss_episodes` and the saved `rss:` identity. Conditional GET supports feeds that reject HEAD; feeds without validators share the six-hour cooldown. Manual/push refresh bypasses it. Anchored playback windows continue chronologically regardless of list sort, matching the PI adapter; blank search terms return no results. Existing imports with legacy freshness capability or missing rows receive an in-place repair, without catalog matching. Refresh re-reads settings after network I/O and checks cancellation/authorization before persistence. Failed/empty feeds retain last-good rows; sticky IDs and removed-from-feed archive rows remain intact. The full-feed semaphore is shared with the PI adapter. Foreground/push persists call the download listener; background discovery suppresses that callback.
- `restoreSubscription` keeps the saved podcast ID across feed URL redirects. Re-adding an existing feed preserves its auto-download and notification settings.

- `RssFeedClient` fetches feeds, handles conditional freshness checks, and parses RSS/Atom data. HEAD 405/501 falls through to a conditional GET (`RssUnchangedLogic`) instead of treating the feed as changed.
- `RssPodcastRepository` implements `RssSubscriptionPort` and manages RSS podcast and episode catalog operations. Refresh and subscribe remap parsed rows through `StickyRssEpisodeRemap.prepare` before writing `latestEpisode` and `rss_episodes`, so stored `episodeId`s never remint. `getEpisodesAround` queries forward-continuation episodes via `RssEpisodeDao.getEpisodesAfter` for same-show queue playback.
- `RssPodcastRepository.legacySubscriptionRepair` exposes `LegacyRssSubscriptionRepair`. `inspect` returns a `LegacyRssFeedSnapshot` without mutating Room; `upgrade` returns a `LegacyRssUpgradeOutcome` and atomically copies a verified RSS catalog under a Podcast Index id without re-keying episodes, and records a trusted alias (`rss_follow_upgrade`) for every copied ID whose key follows the identity contract, so the IDs survive eviction. The copied IDs own their episodes: a trusted owner of the same (show, key) under another ID, left by an earlier read of the show's catalog, is demoted in the same transaction and stays trusted, so a read after eviction comes back under the copied IDs that hold the listener state. When such an owner's ID holds history, a download or a queue entry under any show, the upgrade writes nothing and returns `TARGET_ALREADY_IN_USE`. Both share the per-podcast refresh lock with `refreshCatalog`.
- `LocalEpisodeCatalogRepository` implements `LocalEpisodeCatalogPort`: full publisher-feed catalog under a Podcast Index id, sticky upsert by guid, and a structural per-show ready gate (complete persisted count; a non-null unsubscribe `ttlExpiresAt` is not ready so unsubscribed reads stay on Podcast Index). `getWindow` with `aroundEpisodeId` uses `continuationRows` (`getEpisodesAfter`) to fetch the anchor and subsequent forward chronological episodes. A not-ready catalog always bypasses HEAD validators and performs the repair GET. Listener-id or cached PI-tip mismatches never permanently hide a successfully persisted publisher feed. HEAD/quiet skip and mega GET (capped at 2) remain for ready catalogs. It never creates `rss:` rows; incremental upsert never shrinks existing rows. HEAD validators are not reused after the publisher `feedUrl` changes. `sweepExpired` rechecks TTL before delete so a refresh that cleared `ttlExpiresAt` is kept. `:core:catalog` `SubscriptionForegroundSync` runs that sweep on each launch / Subscriptions refresh pass.
- `StickyEpisodeIdentity` / `LocalEpisodeCatalogPersist` / `FeedOrderLogic` / `LocalCatalogReadyLogic` / `LocalCatalogOrphanRematch` are the identity and freshness helpers. `LocalCatalogListenerStateReconciler` (the orphan rematch) safely re-keys orphaned negative restore ids after a full persist (unique enclosure, then unique title within 48 hours measured in epoch seconds), merging history, sessions/rollups, and queue state into the chosen catalog id. It moves only unresolved legacy negative IDs, after consulting aliases. An ID that a catalog row of any show still holds (an older duplicate row, a changed GUID, an item the feed dropped) or whose alias is trusted or ambiguous (an evicted row's ID, for example) is a known episode, not an orphan, and never moves. An orphan that a new feed item provably owns is never re-keyed either: the read already gave that item the orphan's ID (`ListenerIdAdoption`, below). When a catalog row now holds a trusted orphan's (show, key) under another ID (its row was evicted and the feed read again, for example with a Podcast Index match), the row's ID joins that episode as a trusted alias (`EpisodeAliasProvenance.CATALOG_KEY_MATCH`), so both IDs read as one episode and nothing moves. Only phone-minted IDs with no alias or an unresolved one, whose episode already has a stored row or that match no new item uniquely, are rematched and moved; their history merges into the row the catalog row's episode reads (its owner when the episode is stored under several IDs); merged into another ID's row, it keeps that row's show and episode details, so an owner row of a show switched to its feed stays under that show. The merged like is the latest like decision of the two rows and the episode's group settings (`EpisodeListenerProjection.likeDecision`), so an older like can't undo a later unlike; completion is kept from either row unless the group settings cleared it later. When the match was exact (its enclosure address names one catalog row) and the catalog row has a trusted alias, the moved ID becomes a trusted alias of that episode (`EpisodeAliasProvenance.ORPHAN_REMATCH`), so a later copy of it counts as the same episode and isn't rematched again; a title and date match records no alias. Completed downloads move only when `DownloadCacheRelinker` confirms cached bytes reached the new key; otherwise the legacy row/cache is retained. Ambiguous or metadata-poor rows are retained rather than guessed and no longer block source cutover.
- `ListenerStateMoves` holds the rules for the one path that still moves listener state between stored IDs, the orphan rematch (which IDs are settled, the catalog row that joins a trusted orphan's episode by key, the alias a moved ID gets, the merged completion), and the links that replace the former move when a Podcast Index show switches to its RSS feed (`switchedShowLinks`, `linkWrite`). `SwitchedShowLinker` writes those links. `RssPodcastRepository.confirmPodcastIndexLink`, and adding the feed of a followed Podcast Index show by its address, switch the show without moving anything: history, likes, completion, the queue, downloads, sessions and rollups stay under their stored IDs and show, and no download cache is relinked. Instead, each RSS episode that matches an episode those rows hold gets an alias under the Podcast Index show (`EpisodeAliasProvenance.RSS_SOURCE_LINK`), recorded as a non-owner; ownership then follows the owner rule like any trusted ID. The link is trusted, so the RSS episode reads the old IDs' projected state, its progress goes to the episode's owner and offline playback uses the ID that holds the completed download, when the old ID's trusted key is the RSS episode's key and no other RSS episode has it (for a show the listener confirmed as a lookalike, without the same feed address or podcast GUID, only with the same audio address or title on one of the old ID's rows as well), or when an old ID with no alias or an unresolved one names exactly one RSS episode with a GUID by its exact audio address and no other old ID points at it: that old ID is settled first, trusted under the Podcast Index show with the episode's key (`EpisodeAliasProvenance.RSS_SOURCE_AUDIO_MATCH`, the owner only when the episode has none). Any weaker match (title or date only, a key several RSS episodes share) is ambiguous; a weaker match from another old ID never undoes an exact one. An old ID whose alias is ambiguous links nothing, and an RSS episode whose ID the show's rows already hold gets no alias. Linking is idempotent and runs again after a library backup restore (`RssPodcastRepository.relinkSwitchedShow`), when the RSS show is followed again or restored with its link (`restoreSubscription`), and after every refresh of its feed (`refreshCatalog`, `refreshCatalogIfNeeded`, and each persisted read of `RssEpisodeCatalog`): it adds links for rows that arrived since and turns an ambiguous `rss_source_link` alias trusted once exact evidence exists, never downgrading a trusted alias or touching another alias. A Podcast Index show's namespace for the aliases' recipe IDs is its catalog's stored `epNs`, then the show's (decision D12). Every ID stays as it is, so following the Podcast Index show again keeps everything; its catalog read never reuses a linked RSS ID (`NewEpisodeIds` skips `rss_source_link` aliases).
- `RssIdGenerator` creates deterministic `rss:` podcast IDs and negative episode IDs (mint only, not refresh).
- The episode recipe (`EpisodeRecipeId`) lives in [`:core:model`](../model/README.md), so `:core:database` can use it too. `StickyEpisodeIdentity.catalogKey` delegates to its `catalogKey`, so stored keys don't change. The shared fixture and its test stay here: `EpisodeRecipeIdTest` checks the model's recipe against `src/test/resources/fixtures/episode-recipe-vectors.json`, which the scripts copy also reads. The full identity rules are in [`docs/EPISODE_IDS.md`](../../docs/EPISODE_IDS.md).
- `RssSourceMatcher` provides migration and matching heuristics between Podcast Index and RSS sources.
- `EpisodeSupplementRepository` implements `EpisodeSupplementPort`: fetches a PI show’s public feed and caches **feed-only** episodes under the Podcast Index id. This is **not** a subscription — it never creates `rss:` library rows, never migrates/retires a PI subscription, and never writes FCM topics or autodownload flags. Prefer `RssPodcastRepository` / `RssSubscriptionPort` for true RSS library ownership. Catalog subscription code may read `hasDirectFeedOptIn` when attaching `feedUrl` to notification RTDB rows. `listDirectFeedOptIns` exports HTTPS publisher URLs for library JSON; `restoreDirectFeedOptIn` writes a stub row (no ETag) so import can keep Missing episodes? on even before the feed GET, and does not replace existing extras.
- After a successful feed refresh, `EpisodeSupplementOutcome.Success.newestFeedEpisode` is the tip callers should write to Room `podcasts.latestEpisode` (Home filter chips). A tip that matches a baseline episode keeps its ID and takes every empty field (description, artwork, length, Podcast 2.0 links) from the feed episode (`Episode.withBlanksFrom`), because a match baseline carries only the ID, title, audio and date; a full Podcast Index row is unchanged. `refreshFromFeed` / `optInFromFeedIfDisconnected` fall back to the stored supplement HTTPS `feedUrl` when the request URL is missing or not HTTPS. `refreshFromFeed(RefreshFromFeedRequest)` can load the PI baseline in parallel with the publisher GET; a throwing `loadBaseline` is a feed-load failure and does **not** persist (empty PI must not mark every RSS item as feed-only). `isPublisherFeedUnchanged` HEADs stored ETag / Last-Modified so launch sync can skip GET+PI when the feed did not change. `SubscriptionForegroundSync` and FCM hydration (`NewEpisodePushHydration`) both use `refreshFromFeed` so Home chips and Library get the full extra list; `resolveNewestTipFromFeed` remains the payload guid/enclosure match fallback. Feed load failures return a fixed user-facing message (never raw HTTP/parser text).
- `optInFromFeedIfDisconnected` fetches the feed and persists a supplement **only** when there are feed-only episodes or a newer tip vs the PI baseline; otherwise returns `NoDisconnect` (no opt-in row).
- `EpisodeSupplementListMerge` dedupes PI pages with feed-only supplement episodes using the same identity rules as `EpisodeSupplementMatcher` (audio URL, then non-empty title with a date window). **Page/list merge** (Home, Podcast Info episode list, Smart Queue) runs only in `PodcastRepository`. **In-show search** is a separate union: catalog prefers the network/PI hits; Podcast Info prefers supplement hits so feed-only extras keep their enriched titles.
- `EpisodeSupplementDisconnectLogic` decides auto opt-in on subscribe.
- `EpisodeSupplementArtworkLogic` fills blank item artwork from the feed channel or the PI show image when persisting extras.
- `ports.DownloadCacheRelinker` is injected by app wiring into `LocalEpisodeCatalogRepository`, so the orphan rematch can request download cache relinking without a downloads dependency. Switching a show to its feed no longer relinks anything, so `RssPodcastRepository` takes no relinker.

- Ready catalogs share one persisted six-hour cooldown for `NORMAL` and `AUTO_DOWNLOAD`, including feeds with ETag/Last-Modified. Repair or changed feed URLs bypass stale readiness/freshness assumptions. `MANUAL` and `NEW_RELEASE` force a publisher GET. The shared full-feed gate caps overlapping fetches at two; `RefreshRequest.canProceed` is rechecked after waiting and after fetching so revocation prevents persistence. `isRefreshDue` lets foreground batching exclude recent feeds. The post-persist callback runs outside the transaction/lock and excludes `AUTO_DOWNLOAD` or requests with `runPostPersistCallback = false`; background discovery must admit releases through its own consent and restriction gate.

- `RssHttpExecution` keeps OkHttp cancellation attached through response-body reading. Revoking background consent or leaving a foreground refresh cancels the actual HTTP call; late responses are closed and conditional HEAD cancellation cannot start a fallback GET.

- RSS response consumption keeps coroutine cancellation attached until the body is consumed and closed. The shared response reader validates HTTPS before consuming a response, including redirect responses.

## Dependencies

- Project dependencies: `:core:model`, `:core:database`, and `:core:domain`.
- Libraries: OkHttp, rssparser, Firebase Messaging, and coroutines.
- Tests also use Robolectric and AndroidX Test core, for refreshes through an in-memory Room database.
- Reverse-edge rule: RSS must not depend on downloads, playback, designsystem, analytics, or feature modules.

## Threading / lifecycle

- Production `RssPodcastRepository` is application-scoped through `AppContainer` and shared holders.
- Feed fetch, parse, refresh, and database operations run through suspend APIs on IO-oriented dispatchers.
- Freshness checks share a bounded conditional GET budget and use per-podcast locks to avoid duplicate refreshes.
- Feeds larger than 4 MB skip the RSS library parser, which copies the whole feed into one String and ran out of memory, and use only the streaming pull parser (`RssParsePolicy`).

## Persistence & identity

- Podcast IDs use `rss:<sha256-hex>` from normalized feed URLs and are Room primary keys.
- RSS episode IDs are strings encoding deterministic negative `Long` values to avoid collision with positive Podcast Index IDs.
- RSS episode and podcast rows are persisted in the main database owned by `:core:database`.
- Exact legacy upgrades retain the old RSS row and episodes as an unsubscribed compatibility alias; the active PI row owns an equivalent ready local catalog using the same negative episode ids.
- Switching a followed Podcast Index show to its RSS feed keeps every ID and listener row where it is: the retired Podcast Index show keeps its history, queue, downloads, sessions and rollups, and the RSS show's episodes read them through `rss_source_link` aliases recorded under the Podcast Index show (`ListenerStateMoves`, above). Per-show reads elsewhere count those rows as the RSS show's through `Podcast.listenerShowIds` (`:core:model`). The links live only in Room: a library backup restores the RSS show's `linkedPodcastIndexId`, so the restore links again (by exact audio address, since the backup carries no alias), while cloud sync carries neither, so a device restored from the cloud has no links.
- `LegacyRssSubscriptionUpgrade` stops the RSS follow upgrade (`TARGET_ALREADY_IN_USE`) when a trusted owner it would displace has any history, download or queue row, which is stricter than the owner rule's `holdsListenerState`; an `rss_source_link` owner follows the same rule. `LegacyRssRepair` never picks an RSS show with a linked Podcast Index show, and an upgrade into a switched show's Podcast Index show stops at that show's rows.
- **Feed document order decides duplicates** ([docs/EPISODE_IDS.md](../../docs/EPISODE_IDS.md) §3). Both parsers record each item's position among the feed's `<item>`/`<entry>` elements before sorting, as a `ParsedFeedItem` (`ParsedRssFeed.items`, same order as `episodes`). When items share a catalog key, the first in the document wins, in the parse, in `LocalEpisodeCatalogPersist`, in `StickyRssEpisodeRemap` and in the legacy RSS upgrade (feed items first, then stored rows the feed no longer lists), whatever the publish dates say. `ParsedRssFeed.episodes` stays newest first.
- **Catalog key of a parsed item:** the trimmed GUID, else the trimmed first playable `<enclosure url>` (Atom `<link rel="enclosure">` counts; cover images and other non-media enclosures never count), else the audio address the parser picked (`StickyEpisodeIdentity.feedItemKey`). The audio address differs between parsers when an item also carries `media:content` or several enclosures, and feeds over 4 MB use only the streaming parser, so the enclosure keeps the key the same either way. The two parsers' items are joined by this key, then by minted ID, then by the library's audio address among one streaming item's enclosures.
  - When two GUID-less items declare the same first enclosure (a shared trailer), each is keyed on its audio address instead (`ParsedFeedItem.keyOnAudio`), so they never collapse into one episode.
  - Only the streaming parser reports enclosures. A feed only the library parser can read keys GUID-less items on the audio address the library picked, as older builds did; stored rows are still found (below).
  - An item with no GUID and no playable enclosure (`media:content` only) keeps a phone-only key. The shared contract (docs/EPISODE_IDS.md §1) gives it no identity, so it must never take a recipe ID (`ParsedFeedItem.keyFollowsContract`).
- **Stored rows keep their IDs** (`StoredRowMatch`): a stored row is looked up by the catalog key, then, for a GUID-less item, by its own minted ID when that row is keyed on one of the item's enclosures or plays one of its audio addresses, then by the keys older builds used (`ParsedFeedItem.legacyKeys`, the audio addresses the parsers picked). A row found by its ID or an older key keeps its key, so the write updates it in place. Exact keys are matched for every item before any other lookup, so a row stays with the item that carries its exact key. Synthetic `id:` keys and GUID rows are left to `LocalEpisodeCollisionGuard`. The parser still mints each item's negative ID exactly as before (GUID, else the picked audio address); that mint is how stored rows and legacy rows are found, and the ID items outside the identity contract keep.
- **New episodes of Podcast Index shows take recipe IDs** ([docs/EPISODE_IDS.md](../../docs/EPISODE_IDS.md) §4–5). For an item no stored row holds, `LocalEpisodeCatalogPersist.plan` (with `NewEpisodeIds`) picks, in order: the ID an evicted row of the same (show, key) held, from its trusted alias (owner first, never an RSS episode ID a switch linked; by the catalog key, then by an older key, which the row is then written under); else, for items that follow the contract (`ParsedFeedItem.keyFollowsContract`), an ID only this show's history, queue, downloads or unresolved aliases hold, when the item provably owns it (`ListenerIdAdoption`, below); else the recipe ID of (show, key) in the show's episode namespace, for such items; else the parser's negative mint. Ambiguous aliases never decide an ID. `rss:` shows never reach this catalog, and a show ID that isn't canonical gets no namespace, so both keep phone mints. Each planned row carries where its ID came from (`PlannedIdSource`) and, for a reused ID, the IDs the guard tries if it is taken by then (`PlannedEpisodeRow.fallbackIds`: the key's other trusted alias IDs, then its recipe ID).
- **Listener state stays attached** (`ListenerEvidence`, `ListenerIdAdoption`; nothing is re-keyed). Before recipe IDs, an item no stored row held took its Podcast Index match or its phone mint, so history, the queue and downloads on either ID stayed attached. The read now collects the IDs this show's listener rows and unresolved aliases hold that nothing else identifies (no catalog row of any show, no alias with a key or of another show), and an open item keeps one: first by its own phone mint (the parser's, or `StickyEpisodeIdentity.ownMintedId` of its key or an older key: the same hash input), then by a unique listener match (audio address, else title within 48 hours, run over every item of the feed so a match must be unique; an ID two items match, or two IDs one item matches, is kept by none). This covers played feed-only extras of a show followed later, restored or history-only IDs, catalogs evicted before the upgrade, and episodes played from search or Home under their Podcast Index ID before the show was followed. Each ID is kept by one item at most.
- **Episode namespace (`epNs`).** The refresh mints in the catalog's stored `local_episode_feeds.epNs`, else the show's `podcasts.epNs`, else the show ID (`EpisodeNamespaces.choose`), and stores it where none is stored (`setEpNsIfUnset` on both tables; a stored value is never replaced). `RefreshRequest.serverEpNs`, a namespace the server reported, is only compared: a different value changes no ID and is logged.
- **Aliases from every read** (`CatalogAliasRecords`, written in the refresh transaction through `CatalogIdentityStore` / `RoomCatalogIdentityStore`): a trusted alias for each new recipe ID (`feed_recipe`), reserved ID (`feed_reserved`) and kept listener-held ID (`feed_own_mint`, `feed_listener_match`), one for a stored row that had none (`feed_stored_row`; ambiguous when the ID is in the recipe range but not its key's recipe ID), and the provenance of every healed key (`heal_retrimmed_key`, `heal_synthetic_key`, `heal_audio_url_key`). Unresolved aliases of the show are settled when the read writes their ID under the item's contract key: a stored row found under exactly that key confirms it (`feed_confirmed_key`; the v39 upgrade seeds GUID-less audio-keyed rows unresolved), and a kept listener-held ID or a recipe ID records how it was kept; the alias becomes trusted with the key. A heal on a row whose alias is missing adds one, on an unresolved alias makes it trusted, and on a trusted or ambiguous alias of the same key (the upgrade already re-trimmed padded keys) only replaces its provenance, keeping its state, owner and time. A new alias owns its episode only when no trusted alias of that (show, key) does. Items outside the contract, and rows kept under an older key, get no alias.
- **Test seam:** `RecipeIdHash` is the recipe new IDs are minted with; production always uses `RecipeIdHash.RECIPE`. Collision tests pass a hash that gives two keys the same ID.
- **Older duplicate rows stay.** Older builds could store two rows for one GUID-less item (one per parser's audio address) or for a padded and a plain copy of one GUID. The item now updates one of them; the other stays unchanged and is no longer refreshed, with any listener state it holds (local catalogs, true RSS rows and supplements alike). Nothing joins such pairs yet.
- **Supplement IDs are kept too.** `EpisodeSupplementRepository` replaces a show's supplement rows on every refresh. Feed-only items take the ID of the stored supplement row they match (`SupplementIdentity`, the same lookup as true RSS rows), and a stored row no item matched that holds one of an item's keys (an older build's second row for the same episode) is written back unchanged. Rows of episodes that left the feed or reached the Podcast Index list are still dropped. The tip `resolveNewestTipFromFeed` writes keeps its stored ID the same way.
- Feed read failures are typed: `FeedHttpException` (status code; message unchanged) and `NotAFeedException` (wrong content type or nothing parseable), both `IllegalArgumentException`s. `FeedReadFailure.isAddressGone` reads them, plus no such host and failing certificates, as a dead address (`RefreshOutcome.Failure.addressGone`); timeouts, 5xx, 429 and dropped connections are passing trouble. An address that answers with no episodes counts as dead too. `FeedReadFailure.reportStatus` names what a failed read saw for `/v2/feed-report` (`RefreshOutcome.Failure.reportStatus`): `http_<status>`, `dns`, `timeout`, `tls`, `parse`, `network` or `other`; an address with no episodes reports `parse`.
- Moved feeds: `RssFetchResult.movedTo` is the final address when every redirect was permanent (301, 308; `permanentMoveTarget`); `ParsedRssFeed.newFeedUrl` is the channel's `itunes:new-feed-url` (both parsers). With `RefreshRequest.detectMove`, `confirmedMove` reports a new HTTPS address only when it differs from the saved one and serves the same show by title (case, spacing and punctuation ignored); a declared address is read once to confirm, only while `RefreshRequest.canProceed` still allows a fetch. Temporary redirects never move a feed.
- Address changes keep legacy rows: a catalog read also tries the URL namespaces of the address the catalog was last read from, the address the read was asked for and the address the saved one replaced (`podcasts.previousFeedUrl`, `LocalEpisodeCatalogDao.previousFeedUrl`) (`olderNamespaces`), so a legacy row minted under an old address (synthetic `id:` or audio-address key) still heals to its own ID after the saved address changed or the read was redirected, also when its episode was missing from the first read at the new address; only one earlier address is kept (`LocalEpisodeCollisionGuard.resolve(olderNamespaces)`, `LocalEpisodeCatalogPersist.plan(olderNamespaces)`; `LegacyIdentityRoomTest`, and `LocalEpisodeCatalogPersistTest` for an ID only listening history holds).
- Local catalog writes never replace another episode (`LocalEpisodeCollisionGuard`, [docs/EPISODE_IDS.md](../../docs/EPISODE_IDS.md) §4). The write is a REPLACE, which deletes any stored row sharing the episode ID or the unique (show, catalog key). Inside the refresh transaction, for each row:
  - **Its own stored row first.** When the show already stores the key, the row keeps that stored ID, so it is updated and never deleted through the unique index; an exact stored key wins over one that only matches after trimming. Stored keys are compared after the recipe trim, so a key that Room migration 31→32 left with a trailing newline, tab or no-break space keeps its ID and gets the trimmed key instead of a second row.
  - **Legacy heal.** A same-show row that holds the item's own minted ID (`StickyEpisodeIdentity.ownMintedId`) and whose key is the synthetic `id:<its ID>`, or its audio address while the item has a GUID, is the same episode: it keeps its ID and takes the feed's key. The own mint is looked up whatever ID the row arrives with, so a new item that arrives with its recipe ID heals the legacy row instead of writing a second row under the recipe ID.
  - **A free ID.** Otherwise the row takes its incoming ID when no other (show, key) holds it: no catalog row in the database or earlier in the batch, and no alias of another show or trusted alias of another key of the same show (an evicted episode keeps its ID). An unresolved or ambiguous alias of the same show doesn't block: a recipe ID or phone mint of this key that equals it is that episode's own older ID. A key repeated in one batch is written once (first wins). When a reused ID (an evicted row's or a listener-held one) is taken by then, the row's fallback IDs are tried first (the key's other trusted alias IDs, then its recipe ID), so it takes its recipe ID while that is free.
  - **Reserved ID.** Any other clash (a stored phone mint another show holds, a recipe ID another episode holds) gets a reserved negative ID (`StickyEpisodeIdentity.reservedEpisodeId`), minted in the show's namespace rather than the feed address, so it stays the same across refreshes, address moves and, through its alias, eviction. Reserved IDs from before (minted under the feed address) keep their stored rows.
  - The guard returns the rows to write, the stored keys it corrected with where each old key came from (`KeyRepair`: re-trimmed, synthetic, audio address), the reserved IDs it handed out, and any row with no free ID after 8 reserved tries. The refresh stores the corrected keys' provenance and the reserved IDs on aliases in the same transaction, and logs both. A row with no free ID makes the refresh write nothing and fail, so a partial catalog is never marked complete.
  - The legacy RSS upgrade keeps its IDs for listener state, so it stays on RSS instead when another show holds one, as a catalog row or as an evicted episode's alias. It takes ownership of an episode only from an owner whose ID holds no listener state.
- Package root is `cx.aswin.boxlore.core.rss`.
