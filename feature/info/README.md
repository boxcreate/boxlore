# `:feature:info`

## Purpose

Owns podcast and episode detail presentation: subscribe actions, RSS refresh actions, related and similar content, cross-promotion cards, offline/progress display, and detail-screen layout. It does not own catalog persistence, RSS parsing, download cache behavior, playback services, or app navigation registration.

### Branded show pages

A few shows picked by boxlore get a show page drawn in their own style. `brandedShowPageFor` matches a show by its Podcast Index id, a linked `rss:` copy, its GUID or its feed URL; a match gives the page the pack's colours (page and navbar) through `ArtworkInfoTheme` and `LocalBrandedPage`. The pack draws the identity block above the chips (artwork, wordmark, publisher logo, a © button whose popup holds the copyright line), the "boxlore pick" tag in the top bar and the latest-episode spotlight card. The chips, action buttons and episode list keep their layout and behaviour: the same chips in the same order (the genre chip still opens genre editing), the same buttons in the same order, the same episode cards. Chips take the page's shapes and colours; the action buttons and episode cards keep their usual shapes and take only its colours. Tappable chips keep 48dp touch targets while the row takes only the drawn chips' height in the layout. In the top bar the tag gives way only to the missing-episodes offer, which asks for a choice; the passing feed-check statuses are not shown there.

The page's description sits under the chips, where it is on every show page; tapping it shows the full text and, as on the regular page, the locked-feed notice and the shows the publisher recommends. A page may replace the genre icon pop on Subscribe with its own moment (`BrandedSubscribeMoment`): it draws the whole button in the button's own shape while it plays (the button itself is hidden, so its press shape never shows), holds alerts and auto-download back until its reveal time, then lands on the usual Subscribed state; each run starts from its first frame, and with system animations off it never plays. The Vergecast's is a sticker slap: its wordmark sticker flies in, lands with impact lines and one light haptic, and the button wipes to Subscribed, about 1.2 seconds. A page's header can follow the same moment through `LocalBrandedHeaderMotion`, which also says when one of the show's episodes is playing.

The spotlight shows the newest full episode while the list is newest first and search is closed, with the list's like, download, queue and play actions, progress and played state; the list leaves that episode out. Sorting oldest first or searching hides the card and the episode returns to the list.

## Threading / lifecycle

- ViewModels are scoped by app navigation. Post-subscribe local-catalog ingest is owned by application-scoped `SubscriptionForegroundSync`, not the Podcast Info ViewModel. Late page-load, metadata, and direct-feed responses preserve the current subscription state, so work started while subscribed cannot undo a completed unsubscribe.
- Catalog, local catalog, offline lookup, RSS, download, playback, and analytics dependencies are supplied by app wiring.
- Podcast/episode info emits glossary analytics via `:core:analytics` façades (no PostHog direct).
- UI runs on the main thread; refresh, subscribe, lookup, and related-content work use suspend APIs.
- `EpisodeInfoScreen` delegates description and link list entries to a focused show-notes builder, preserving their order, formatting, visibility and chapter-seeking callback.
- `EpisodeInfoNotesLoader` parses publisher HTML on a background dispatcher, fetches chapters and promotion matches independently, and cancels superseded requests. A generation guard also rejects late responses during metadata refreshes for the same episode. Invalid/empty remote chapters retain the description fallback; promotion failures do not block description or chapters.
- Episode lists never repeat an id: `remountWithSupplements` and the displayed list drop duplicates, because offset pages overlap when episodes publish between "load more" requests and the list keys rows by episode id.
- **Loading and empty states (30 Oct 2026).** Opening a show draws the page in its own shape (`ShowPageSkeleton`: cover, title, chips, description, buttons, two episode cards, shimmering in the page's surface tones) in place of the lone 80 dp loader, under the same `podcast_info_loading` tag. Loading more at the end, and the archive read for oldest first, show two loading episode cards (`EpisodeCardSkeleton`, `EpisodeListItem`'s geometry) in place of the wavy spinner. **Hide completed episodes** used to filter only the loaded episodes, and the next page loaded only when the last row was drawn, so with every loaded episode finished the page stayed blank (listener report on 0.0.29, worst after reversing to oldest first). Now, while fewer than `HideCompletedFill.MIN_VISIBLE` (8) unfinished episodes show and the show has more, the page asks for the next page by itself (`rememberHideCompletedFill`), showing "Completed episodes are hidden. Finding the ones you haven’t finished…" with the wavy progress and loading cards; a feed read's own line takes precedence. When the show runs out with none left, `ShowCaughtUpCard` says "You’ve finished every episode" and offers **Show completed episodes** (`toggleHideCompleted`). Search ignores all of this, as before.
- **Show page state across window changes.** Resizing, rotation, split-screen and fold posture changes keep the same live page, so everything on it stays put. Activity recreation (a density change while folding, or process death) and a return from the back stack also keep open search, the five dialogs and sheets (mark all played, mark all unplayed, show playback, tag/genre edit, missing episodes), the tag/genre draft, the scroll position and the episode selection, all through saved state. So a listener who leaves the page with episodes selected finds them still selected on return; opening an episode from search results closes search first, so Back returns to the full list. The sort, hide-completed and refresh state live in `PodcastInfoViewModel`, and so does the live search query. `loadPodcast` skips a repeat call for the requested route ID even when the page now carries another ID (a followed `rss:` feed linked to the show, or the catalog ID from show details; `PodcastInfoLoadGuard`), so recreation and back-stack returns never reload those shows either. After process death the new ViewModel starts with an empty query, so the page saves the query too and runs the search again once the first page has loaded; the result list's scroll position is not kept in that case. Restored search does not scroll the list or reopen the keyboard; only tapping Search does. Selection is saved as episode IDs, the anchor and the sort it was made in. A recreated page waits until its first page has loaded (`PodcastEpisodeSelectionLogic.canRestoreSelection`), then looks its selected episodes up again from the loaded list and from the selection window, read in the saved sort (`loadEpisodeSelectionWindow(sort)`), keeping that window's order for the actions. IDs neither can supply are dropped, so the count matches what the actions receive. While the lookup runs, the selection toolbar's actions are disabled (`EpisodeSelectionToolbarState.actionsEnabled`) and the range menu shows progress. A failed lookup (for example offline) keeps every ID with the actions still disabled and tries again when the page state next changes; Back or Clear ends the selection. A restored Missing episodes? dialog shows only while the reloaded page offers the feed check, and is dropped once the check has run.

## Persistence & identity

- **Episodes stored under several IDs.** The like state on the episode page and the show page reads `PlaybackRepository.likedEpisodeIds`, and the show page's per-episode progress reads `historyForEpisodeLookup`, so an episode stored under several IDs shows its like and progress whichever ID the page lists ([`docs/EPISODE_IDS.md`](../../docs/EPISODE_IDS.md) §5). A seek saved from the episode page writes the episode's owner row and keeps its like as stored. The download and queue indicators and toggles read `DownloadRepository`'s alias-aware download state and `PlaybackRepository.withEpisodeAliases` for the queue, so on a show switched to its RSS feed an episode the old Podcast Index show downloaded or queued shows as downloaded or queued, and its toggle removes that download or queue entry instead of adding a second one. Episodes stored under one ID read and write as before.
- **Try these episodes (More like this) switch** (`DiscoverySections.moreLikeThis`, Settings → Library → LeaveMeAlone): `EpisodeInfoViewModel.moreLikeThisOn` hides the section and its loading card while off or unread. `collectSimilarEpisodes` (`logic/SimilarEpisodesLoader.kt`) loads it through `collectDiscoverySection`, so off makes no request, turning it off cancels the request in flight (the repository call is a cancellable `awaitResponse`), and turning it back on loads it for the open episode. Replies land only on the episode they were for, and starting a different episode cancels the previous loader at once. `SimilarEpisodesLoaderTest` covers off, on, switching off mid-request, switching back on, a reply for an episode no longer shown and a failed request.
- This module owns no storage files or stable keys.
- Pin reads and writes `home_pinned_podcast_ids` through `:core:prefs` (`toggleHomePinnedPodcastId`). At-capacity copy comes from `HomePinnedShows.capacityUserMessage()`. Notification permission prompt history is tracked via `has_requested_notification_permission` in `BoxcastPrefs`.
- Podcast, episode, RSS, download, and listening-progress identities come from core modules.
- App navigation owns route patterns and deep links.
