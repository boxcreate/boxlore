# `:app`

## Purpose

The application module owns the Android app shell: `BoxLoreApplication`, `MainActivity`, navigation wiring, FCM entry points, in-app announcements, surveys, OPML import UI, and the single production composition root in `AppContainer`. It wires feature screens and core services together; feature UI and data engines remain in their owning modules.

## Public API

- `TabletAppShell` retains primary/detail navigation hosts while resizing their physical regions. Tablets use the existing four destinations in a Material rail; wide landscape windows show a 360–520dp context player/detail pane and close it when empty. Card grids use the supplied pane width. Details, Back, external routes, Brief redirects and palette ownership stay within their route owner. A hidden detail host drops to CREATED so it cannot intercept Back or continue active UI collection. Warm links that open in the context pane keep the empty context root beneath the linked screen, so Back and closing details return to browsing. When a retained detail covers the primary pane after rotation, a fold or a narrow resize, rail and bottom-bar taps close it before navigating so the tapped destination is visible.
- `TabletAppPlayer` reuses the existing docked mini/full scaffold in single-pane windows and the bounded full player in context. Full-screen playback has its own explicit action. The app's retained player UI scope keeps supporting tabs and expansion across reflow once a tablet layout has been shown in this Activity; until then phones keep the original per-player state and reopen the sheet collapsed. Playback repositories remain owned by `AppContainer`. A minimized context player returns to its pane when the listener reopens it: tapping the docked mini player in a split window, or expanding it in a single pane and then widening to a split window. Tablet players start from the current playback state, so their first frame is never blank. A detail pane beside the docked mini player does not reserve the mini player's height. On foldable windows, the mini bar docks inside the browsing region and expands into a full-window fold-safe player canvas. Tablet content clearance reserves the docked player/taskbar without a phantom bottom bar.

- `BoxLoreAppRoot` computes one `BoxloreWindowLayout` and provides it through the design system. Stable Adaptive's window metrics and WindowInfoTracker-backed folding collector react to resizing, multi-window and posture changes; feature/data producers are not restarted. Native folding bounds convert from window pixels to dp once. Configuration dimensions remain available separately for existing phone geometry. Adaptive 1.1.0 preserves the current Compose graph: 1.2.0 requires Foundation 1.9.0 and 1.3.0 requires Compose 1.10.0. The Compose BOM is unchanged. Player detail-route helpers preserve existing encoding, metadata fallbacks and Brief routing while keeping the app root below the source-size limit.

- Appearance wiring exposes the persisted full-player style and forwards selection to `:core:prefs`. The existing player overlay chooses the audio presentation without changing navigation, player ownership, playback or the miniplayer. Standard remains the default, and video retains its current presentation.
- The Floating navigation bar can sit over a blur of the page (`FloatingNavigationBlur`, Settings > Appearance > Blur behind the bar: Off / Soft / Medium / Strong, Soft by default). The shell marks the page as a Haze source (`dev.chrisbanes.haze` 1.6.9, which adds no Compose version) and draws one blur strip, on a scaled-down copy, behind the bar: sized to the bar and system inset plus the level's reach above the bar. The mini player is left out, so the strip keeps its size when playback starts instead of growing up behind the player. An eased mask (cubic ease-in) fades blur and tint in together over the reach, so the top edge never shows. Levels set the reach (28 / 40 / 56dp), blur radius (8 / 14 / 22dp) and page-colour tint (6 / 14 / 26%). The bar and mini player stay solid; nothing blurs with the Classic bar or Off. `FloatingNavigationBlurTest` covers when it shows, that each level is stronger and reaches higher, the fade curve and the strip height.
- The shell passes the Home hero card style (Settings > Appearance > Home hero cards) into the settings state; Home reads the same preference directly. `BoxLoreAppRoot` also syncs the current hero style and colors, default included, to analytics person properties (`syncHomeHeroStylePersonProperties`), which sends once per process and on each change.
- `BoxLoreAppRoot` collects `discoverySectionsStream` (initially all on, `DiscoverySections()`) into the settings state. Settings > Library > LeaveMeAlone reads it through `RegionSettings`, and Navigation reads it to hide Explore opens to without For you. Writes go through `setDiscoverySection`; a failed DataStore write is logged and leaves the stored value, which the switch keeps showing. Home, Explore and episode pages read the same stream directly.

- Brief navigation injects the shared preference repository. A missing region uses the independent saved Brief edition; explicit Home, episode, podcast and notification regions keep their existing route precedence.

- Coil is installed once in `BoxLoreApplication`, before widgets/services start, so activity recreation does not replace their shared image cache. The shell supplies failed-image recovery on foreground reentry and reconnection. Episode push hydration retains episode/show artwork candidates and a six-second total artwork budget; general push artwork uses a four-second budget. Notification routes, sounds, audiences and delivery guards remain unchanged.

- The app-scoped updater checks on foreground at most every six hours (failed requests back off for 15 minutes). Settings → Check for updates bypasses the interval. The Home/Library utility capsule gets an icon-only action only for a confirmed newer compatible version. Background checks never open a prompt or start a download. Direct installs read a bounded versioned `update.json` from GitHub Latest, cache the last valid offer and distinguish connection errors from an up-to-date result. Same-version artifact refreshes stay quiet.
- Direct APK updates use an app-private, checksum-keyed resumable transfer. Download, verification and installation are separate explicit actions; the Android installer owns confirmation. Before each handoff, the APK's checksum, package, exact version, Android minimum and signing identity are checked again. Interrupted transfers resume; failed integrity checks discard corrupt bytes. Returning from install permission settings or cancelling Android installation retains the Install action. A changed offer discards stale prepared state. Restoration separates session eligibility from verified-file recovery and retains cancellation and checksum guards.
- `assembleRelease` builds the direct APK. `bundlePlayRelease` builds the Google Play AAB with release optimization/signing, the same application identity and normal notification receiver, but no APK downloader/installer implementation or `REQUEST_INSTALL_PACKAGES` permission. Play availability uses Play Core and caches the confirmed version across process recreation; the explicit action obtains fresh eligibility before starting a flow or finishing a downloaded flexible update. In-progress immediate Play updates resume on foreground. Release artifact validation checks both variants separately, including installer exclusion in Play.
- Announcements use native Material 3 Compose surfaces, typography and buttons. Compact alerts and full-screen messages have a fixed category/close header, scrollable Markdown and optional image, and fixed actions. Controlled accent roles, banner/uncropped cover, headings, lists, callouts, links and emphasis are supported; payload HTML remains text. Release alerts have Download update (native metadata check and transfer), View on GitHub (keeps the alert on return), and Dismiss. Normal alerts retain their optional single action. The browser admin preview follows the same visual specification without executing in the app.
- Built-in feature announcements, such as the Android Auto overlay, spell the product name boxlore in lowercase; `:core:testing`'s `BrandNameGuardTest` enforces this for app copy.
- Announcement payload additions are optional and persist with legacy defaults. Only release alerts are install-channel/version filtered; ordinary and new-episode notifications remain available to both channels. New Play/direct builds retain ordinary broadcast topics and register their install channel. Release sends use direct_users while excluding Play/test topics, with an explicit include-Play override via All installs. Older clients cannot be classified through their shared prod_users topic, so they do not receive these new strict direct-only release sends until updated; the legacy payload/window remains readable for normal sends.
- The updater persists its visible/prepared session through permission settings, Activity recreation and process restart. Opening it refreshes metadata automatically, retaining cached notes while checking and without starting a download. An announcement Download action performs one refresh before transfer. Available-update screens have no redundant check button; failed/current checks retain recovery controls. Its unboxed release-note paragraphs scroll between a fixed header and full-width download/install controls, keeping progress and actions accessible for long notes. Restoration verifies an existing completed file without starting a new transfer or installation. Missing files return to Download; an explicit Install tap rechecks the package/signature and retries Android's permission or installation flow. Completing an update clears the obsolete session on the next app start. Update offers/session preferences are excluded from cloud/device backup.
- `assembleUpdateTest` is signed and optimized like release, uses a loopback-only test manifest and test-only metadata, and subscribes only to test_users for announcements. Its ADB-only AnnouncementTestReceiver previews an exported message locally without FCM; this receiver and test marker are rejected by shipping artifact checks. Test update/session preferences are separate. Its mapping upload and Crashlytics collection are disabled, and analytics mark it internal. Test builds must never be published; they intentionally keep the package/signature so installation can preserve listening data.


- While native predictive Back is held over a regular destination such as Home, the shell previews the saved theme for navigation and its canvas. Cancelling restores the detail palette. Only detail destinations inherit the departing palette (loaders and the canvas under the pages); going back to a regular page such as Home shows the saved colours from the first frame, with no detail colour left on the canvas or loaders while the pages slide. Scaffold foreground ownership prevents inherited black text in dark previews. JVM tests drive real Back start/progress/cancel events without committing.
- Custom theme saves are emitted through the analytics facade after preference persistence succeeds, separately from selecting an existing theme.

- The composition root shares `SubscribedEpisodeCatalog` across foreground sync, subscriptions, automatic downloads and FCM hydration. Pure RSS push hydration fetches the saved URL and matches GUID/enclosure to the original negative ID without a PI lookup or newest-item guess. Podcast Index shows' catalog refreshes (push hydration, foreground sync, auto-download, restore) never read a Podcast Index list: new episodes take recipe IDs in `:core:rss`. Only the feed-only extras path without a local catalog compares the feed with the PI list (`loadPiEpisodesForSupplement`, up to 1,000 newest episodes). RSS notification disclosure consent is stored outside backups and is tied to the saved URL. No new on-device periodic notification worker is scheduled; existing optional background auto-download discovery remains independently consented.
- RSS pushes must match the current saved feed URL before immediate display or durable hydration; the worker rechecks subscription and URL after hydration, and notification rendering rechecks local consent after artwork loading. `RssNotificationSyncWorker` reconciles journaled RTDB registrations and FCM topics with network constraints and retry backoff. Settings changes, app-root reconciliation (even with the restore sentinel present), and token changes restart this non-polling worker without waiting behind an earlier retry's backoff; incomplete cleanup survives restart and retries without a maximum-attempt cutoff.

- `NavGraphLibraryDestinations` routes New Episodes row and Play All snapshots through `QueueManager.playContextEpisodes`, so playback follows the visible list rather than reusing a prior show queue.
- `LoreQueueConflictDialog` confirms **Start a Lore queue?** when a Lore card's queue action encounters a non-Lore queue. Localizable copy explicitly states that **Start Lore queue** stops playback and replaces the current queue with the selected episode, then explains swiping right on other Lore cards to add more. **Keep current queue** cancels that operation; the help directs listeners to tap a card to open its episode details and choose **Add to queue** to preserve the existing queue. Queue operations and analytics result keys remain unchanged.

- `BoxLoreApplication.container` exposes the process-scoped `AppContainer`.
- Settings > Appearance previews come from the app wiring (`NavGraphSettingsDestinations`), which passes Home's `HeroStylePreview` with the listener's resume sessions, so Settings shows the real hero cards without depending on the Home feature.
- On startup, `BoxLoreApplication` hydrates missing DataStore appearance keys from theme fast-cache on its IO scope, keeping restoration off the first-paint path (Google Backup can restore SharedPreferences without DataStore), and after UI readiness asks `SmartDownloadManager.reconcileScheduleWithPreferences` to keep the Smart Downloads toggle and periodic WorkManager job in sync. It also configures `LearningEventLog` via `BoxcastPrefs.resolveLearnerLogEnabled`: on by default in debug when unset; **always off in release** unless the user has explicitly persisted an opt-in from the debug screen. Once startup work is allowed and before cloud sync starts, it also repairs player-only artwork links that older builds saved into history and the queue (`repairPlaybackArtworkLinks`), so Jump back in shows real covers, history rows that found a real cover upload, and a changed queue is pushed again; with nothing left to repair it changes nothing.
- `AppContainer` constructs the shared graph: database, network, auth (`authRepository`), RSS, ranking, catalog, folders (`FolderRepository`), playback, queue, downloads, prefs, and analytics dependencies. It provides the narrow `DeviceIdentityPort` (delegating to `BoxcastPrefs.getOrCreateSyncDeviceId()`) to stamp local mutations for cross-device sync. It constructs `UserSyncCoordinator` with real DAOs, conflict resolvers, and token providers, and wires `CloudSyncTriggerCoordinator` to observe process lifecycle, playback milestones, database mutations, and connectivity state. It builds `LocalEpisodeCatalogRepository` with the main Room database and the downloads-owned cache relinker, allowing a repaired full feed to transactionally re-key safely matched legacy listener ids (phone-minted IDs with no alias or an unresolved one) without creating a reverse module dependency. `RssPodcastRepository` gets no relinker: switching a Podcast Index show to its RSS feed links the feed's episodes by alias instead of moving downloads. It gives `AdaptiveCandidateScorer` the database's `EpisodeListenerStore.groupTokens`, so ranking counts an episode stored under several IDs once, gives `HistorySyncResolver` `EpisodeListenerStore.memberIds`, so a pull never overwrites the playing episode's progress under its owner ID, gives `UserSyncCoordinator` the `EpisodeIdentityDao`, so an account switch clears the shared like and completion settings with the history, and gives `UserSyncCoordinator` and `QueueSyncResolver` one `SyncEpisodeIdentity`, so synced history and queue rows carry their episode's recipe ID and catalog key, pulled rows are recorded as aliases before they are merged, and the queue merges per episode. The catalog instance is shared by `PodcastRepository`, `SubscriptionRepository`, `SubscriptionForegroundSync`, and FCM hydration. The same application scope owns `LegacyRssRepair`.
- Cloud Synchronization (`sync/`): `CloudSyncWorker` runs guaranteed background synchronization via WorkManager (`schedulePeriodicSync` every 6 hours with network constraint, `enqueueOneShotSync` on app backgrounding or network recovery), mapped in `LegacyWorkerFactory`. `CloudSyncTriggerCoordinator` binds to `ProcessLifecycleOwner`, auth state flows, network connectivity changes, and player milestones (PAUSE, COMPLETED, track changes) to trigger non-polling, battery-friendly delta pushes and pulls, and clears the active playback session on sign-out. It exposes `syncStatusFlow` (`Idle`, `Syncing`, `Success`, `Error`) and `triggerManualSync()` consumed by the Account Settings screen.
- **API sessions (`session/`, 2026-10-17).** `BoxLoreApplication.onCreate` calls `ApiSessionSetup.install` before anything else, so the shared `/auth/session` exchange (`:core:network` `ApiSessionManager`) starts behind the splash and no request goes out before the manager exists. This build sends only `X-Boxlore-Session`, never the bundled app key. The setup sets `X-App-Version` and `X-App-Channel` (`InstallChannel`: `play` for the Play build or a Play install, else `github`; the same rule picks the update flow in `createAppUpdates`), installs App Check (debug provider in debug, Play Integrity in release) with background auto-refresh off, and supplies App Check only to the exchange (`FirebaseAppCheckTokenSource`, failure categories from `AppCheckFailureReason`). The old blocking App Check provider, which made every request wait up to 5 s, is gone. `observe` passes process foreground/background (`ProcessLifecycleOwner`) and connectivity to the manager, which retries App Check for limited sessions only in the foreground with a network. `ApiSessionAnalyticsListener` forwards session events to `api_session_status` and each App Check attempt to `app_check_status` with its reason.
- **Turnstile step-up (off by default).** When a limited session reaches an AI onboarding route, the manager asks `TurnstileStepUpController` for a token. `TurnstileStepUpHost`, composed once in `BoxLoreAppRoot` inside the window-layout provider, loads `<API base>/auth/turnstile` (a static page on the API host) in a locked-down WebView (`TurnstileWebViewPage`, following Cloudflare's mobile guide: JavaScript, DOM storage, cookies including Turnstile's third-party frame, and the default user agent; but no file or content access, no new windows, top-level navigation limited to the API host, `challenges.cloudflare.com` and `about:blank` / `about:srcdoc`, and an `androidx.webkit` message listener that accepts the `BoxloreTurnstile` bridge only from the API origin). The page runs invisibly inside a zero-size parent (laid out but never drawn, touched or announced) while onboarding keeps its normal thinking state. Only if Turnstile asks for interaction does the same page move into the shared `BoxloreModalBottomSheet` (a phone sheet; a centered dialog on expanded and folded windows) with “Quick check”, a short reason and **Skip**. A run with no answer within 20 s (or 2 minutes once interactive), a page error, Skip, Back, a swipe or an outside tap fails it, and onboarding carries on with its non-AI path. The step-up runs only while the PostHog flag `api-turnstile-step-up` is on; the flag does not exist yet, so it stays off until the API's Turnstile secret is set. Copy lives in `res/values/session_check.xml`.
- Authentication & Deep Links: `MainActivity` handles incoming App Link intents for `https://boxlore.in/auth` (and `https://aswin.cx/boxlore/auth` from links sent by older builds) to complete passwordless email link sign-in via `authRepository.signInWithEmailLink`. It prevents one-time link replay across activity recreation by nullifying intent data and tracking consumed links, and prompts for the user's email via `CrossDeviceEmailDialog` if a magic link is opened cross-device without local pending auth state. Sign-in goes through `AppContainer.emailLinkSignIn` instead of toasts: each new link raises an Account page request, and `BoxLoreAppRoot` opens Settings on Account & sync (`ACCOUNT_PAGE_ROUTE`, unless `isAccountPage` says it is already showing; before onboarding finishes Settings shows the onboarding version), where the page shows Signing you in, then the first sync, or why the link failed. `accountPageRequestAction` decides each request (ignore one already handled, including across recreation, since the handled value is saved with `rememberSaveable`; only mark it handled when Account & sync is already showing; otherwise open it), and `AccountPageRouteTest` covers it and the route check. `BoxLoreApplication` configures `NetworkModule.authenticator` with `FirebaseAuthAuthenticator` at startup to automatically refresh STS tokens on HTTP 401.
- Install attribution: `AppContainer` wires `InstallReferrerManager.onInstallReferrerResolved` → analytics person properties (`install_channel`). Catalog stays free of `:core:analytics`.

- **Feed fix off switches** (`sync/FeedFixSwitches`): PostHog kill switches for the feed and episode fixes, passed into core modules as lambdas. A fix runs unless its flag is on; no answer (PostHog not ready, flag missing or inactive, an error) keeps it on. `feed-fix-match-baseline-off` sends the feed-only extras' comparison list back from the 1,000-item `episodes/match` list to the 100-item page (`PodcastRepository.useEpisodeMatchBaseline`). `feed-fix-address-recheck-off`, `feed-fix-sync-fallback-off` and `feed-fix-moved-feed-off` turn off the subscription sync's dead-address re-check, its `/sync` fallback for failed feeds, and following moved feeds (`FeedFixToggles`). `FeedFixSwitchesTest` covers the default. The same fail-open switches pause the v2 build's jobs: `upgrade-repair-off` (the one-time repair of saved feed addresses after the update), `address-check-off` (the daily address check of followed shows), both without marking the work done, and `v2-discovery-off` (discovery back on the v1 routes). These three are read through `sync/SavedKillSwitch`, because the repair can start on a headless launch before PostHog is set up: once PostHog is ready its answer decides and is saved; while it is still starting, the last saved answer is used, and the job runs only when none was saved.
- **Feed-first rollout** (`sync/FeedFirstSwitch`): the `feed_first` PostHog flag picks where show pages read episodes (on: the show's own feed; off: the server's list). Unlike the off switches it fails closed: with no boolean answer from PostHog it uses the last saved answer, else off. The first read fixes the value for the process, so a page's source never switches while the app runs. `$feature_flag_called` is recorded once per process, only when the value came from a live PostHog answer, and the process uses the value that exposure read returned. `sync/RolloutFlagMemory` saves `feed_first` and the three switches above for the next process whenever PostHog reports loaded flags (`PostHogAndroidConfig.onFeatureFlags`: the startup preload, `identify` and `reset`; explicit `reloadFeatureFlags` calls don't reach it, so a mid-session change is saved at the next of those loads). To roll back, keep `feed_first` active with a 0% release condition so phones get and save `false`; never disable or delete it before the flag's removal, because a disabled flag is missing from PostHog's answer and a phone that saved `true` would stay on. `AppContainer.rolloutSwitches` hands `feed_first` and the three switches above to `:core:catalog` as `RolloutSwitches` on `PodcastRepository`; nothing reads them yet.
- **Feed reporting** (`sync/AnalyticsFeedTelemetry`): `AppContainer.feedTelemetry` is the `FeedTelemetryPort` handed to catalog code, so feed reads and address swaps reach `feed_fetch_result` and `feed_url_corrected` without catalog depending on analytics. A reporting failure never reaches the caller (`AnalyticsFeedTelemetryTest`).

- `BoxLoreNavHost` owns app route registration and delegates screen bodies to feature modules; stack-slide transitions follow the visible Home → Explore → Library → Lore order, and Home’s first committed content frame unlocks the floating Lore launch animation.
- `NavGraphPodcastEpisodeDestinations` registers episode and podcast detail routes; episode full-path routes define `episodeDescription` as nullable with a default null value to safely handle empty, omitted, or special-character descriptions without argument bundle verification failures.
- `NavGraphSettingsDestinations` registers the settings hub, category pages, download settings, the dedicated `"feedback"` full-page destination wired to `:feature:settings:feedback:FeedbackScreen`, and the Support sub-page within the `"settings"` route (selected with `settings?page=support`), rendered by `:feature:settings:pages:SupportDevelopmentPage` (with listening-hours insights flow and support screen visibility callbacks to hide player chrome).

Account and onboarding hide the player overlay even when cloud restore introduces a current episode, while audio and playback state remain service-owned. Direct account entry suppresses chrome immediately from its route arguments; leaving Account restores normal player presentation. The existing Support and mode-switch suppression remain in place.
- Cold-start destination precedence (see `StartDestinationResolver`): incomplete onboarding → offline Downloads (no deep link) → Appearance **Open app to** Subscriptions or Downloads (no deep link) → Home. Offline-forced Downloads without that pref still exits on Back. That Home navigation is owned by `PredictiveBackWrapper` (NavHost has nothing to pop), so peek scale must restore after the gesture — see `:core:designsystem`.
- Process latest-episode sync (`SubscriptionForegroundSync`) and the versioned legacy RSS repair are started from `BoxLoreAppRoot` after onboarding. Repair is enabled only for upgraded installs running `0.0.18` through `0.0.30`, except `0.0.20`, starts only while online with at least one eligible pure `rss:` subscription, and admits at most one pass per app process. A fresh install on an allowed version writes the completed marker without inspecting or changing catalog rows, so updating a fresh `0.0.18` install to `0.0.19` cannot enable repair later. Unsupported versions and invalid package metadata fail closed. App foreground/screen-on events do not request another pass. While an eligible pass is active, the shell shows a persistent top popup with the boxlore loader; it cannot be dismissed and disappears when the pass settles. Returning to the app still requests normal subscription refresh (`SubscriptionResumeRefreshLogic` skips the first `ON_START` so Home keeps its 2s first-paint delay). Subscriptions-first launches still fetch because Library calls `requestRefresh` as soon as that screen is visible. Identified FCM payloads (guid/enclosure) that do not match a local episode no longer fall back to an unrelated newest tip.
- Tab destinations in `NavGraphTabDestinations` wire Home / Explore / Learn / Library / player entry points to feature screens. Home’s Offline Mix “View all downloads” action navigates directly to Library Downloads through this shell-owned wiring. Lore history deep-links use `entryPoint=learn` (canonical glossary; legacy `learn_history` still normalizes to `learn`). Explore and Subscriptions apply Appearance **Default tabs** when the route does not already pick a tab (genre Explore, `tab=trending` / `for_you`, and `library/subscriptions?tab=0|1` still win).
- Home receives the shared catalog and ranking instances it actively uses; endpoint-backed
  editorial rows are loaded inside `:feature:home` through that catalog instance.

- New-episode FCM callbacks persist GUID/enclosure hints in unique delivery work before network I/O. Push hydration still bypasses automatic freshness limits and remains independent of background polling consent. `AutoDownloadLifecycle` gates the existing subscription refresh timer with process foreground state, replays cached claims on foreground entry without another RSS sweep, and reconciles explicit background-check consent and transfer constraints. Startup cancels historical catch-up jobs and automatic transfers whose discovery source is unknown; cached claims remain recoverable on foreground refresh or push. Background consent is excluded from legacy backup, cloud backup, device transfer, library export, and cloud settings. Only foreground/manual/import/push catalog persists invoke the ordinary download callback; background discovery admits its own releases through its runtime gate.

- Delayed notification hydration updates only the matching active release; dismissed alerts and newer releases are preserved, including after artwork I/O. Hydration exceptions and unresolved releases share a five-retry limit. On startup or a Wi-Fi policy change, automatic transfer reconciliation compares persisted work constraints and cancels only mismatches, preserving correctly scheduled cold-start workers.

- Download lifecycle reconciliation scans cached release claims only while the process is foreground. Resume and preference reconciliation share `AutoDownloadForegroundScan`: process stop cancels its owned job, each show rechecks foreground state, and in-flight enqueue admission uses the same live guard. A later foreground entry replays interrupted pending claims. Push admission can replace pending background-gated transfers before lifecycle cancellation finishes.

## Startup scheduling

Unacknowledged tablet launches first show an opaque alpha notice with the Home feedback icon and OK. The Activity latches this initial-window decision through recreation and resize. It needs both the tablet window gate and a display whose shortest side is at least 600dp, so phones never show the notice or read its acknowledgment, even when a landscape window at a small display size passes the tablet gate. The app root, Welcome/onboarding owners and sign-in portal are not composed until OK, which persists a separate local acknowledgment. Cached appearance settings theme the notice, and its body scrolls in short fold-safe regions. NPS, queued SDK surveys and update presentation wait behind this gate; post-OK prompts resume after app frames establish playback state. The visible notice releases ordinary deferred startup work after its own first frames without creating Welcome.

`StartupWorkGate` is process-scoped and releases optional cloud coordinator initialization, periodic sync scheduling, Smart Downloads scheduling/catch-up, foreground subscription sync and legacy RSS repair after the initial screen commits. Optional initialization uses a suspending mutex so ready does not release a burst of initializers. Home signals after loaded local content and two frames; other initial routes release after their first two frames. A headless worker/widget launch releases at the first idle main queue; `MainActivity` identifies a UI launch before creating content. If the first Activity stops before content is ready, background startup also releases; configuration recreation waits for the replacement UI. Recreated roots reuse the same gate. Repeated signals and cancelled initializers are safe (`StartupWorkGateTest`). Adaptive ranking telemetry also waits for readiness. Appearance flows use restored fast-cache values while background hydration fills missing DataStore keys; existing choices are never overwritten. Play update checks begin after the first two Compose frames. Playback/session restoration and preference identity remain owned by the existing composition root.

- Release runtime dependency snapshots include Jsoup through `:core:catalog`, which owns shared show-notes resource and chapter parsing. No direct parser-library dependency is added here.
`BoxLoreApplication.onCreate` never builds `PlaybackRepository` for Cast state. `AppContainer.synchronizeCastSession` keeps the latest state in `DeferredCastSessionState` and applies it when playback is first created, so widget, worker and notification starts no longer construct playback (prefs migration, MediaController bind) on the main thread. PostHog setup runs on a background thread through `:core:analytics` `PostHogStartup`, and environment super-properties are registered before queued calls replay. Navigation string arguments encode the literal text `null` as the `_` placeholder, because Navigation reads it as a null argument.
